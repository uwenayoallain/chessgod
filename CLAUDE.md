# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The root `Makefile` is the authoritative command surface:

```bash
make run            # docker compose up --build (full stack: Postgres + Redis + backend + frontend)
make down           # stop the stack
make test           # run both suites
make backend-test   # cd backend && .venv/bin/pytest
make frontend-test  # cd frontend && vp test
make frontend-check # cd frontend && vp check
make frontend-build # cd frontend && vp build
make theory-sync    # seed ECO openings and refresh Lichess master data
make db-backup      # refresh backups/chessgod.dump if the player's data grew
make db-restore     # replace the database with backups/chessgod.dump (asks first)
make db-backup-schedule  # install the daily 04:30 systemd --user timer
```

**Backups are one file, refreshed when the player's data grew.** `backups/chessgod.dump` (git-ignored) is a `pg_dump -Fc` archive written through the postgres container by `scripts/db_backup.sh`: 2.5 GB of database come out as ~125 MB, in ~25s. The script fingerprints the player's own tables (games, training events, evaluations, line memory, engine games, repertoire marks) and dumps only when that changed — the master-theory sync rewrites position stats around the clock and does not count — writes to a `.part`, verifies it with `pg_restore --list`, then swaps it in, so a failed dump never replaces a good one; a dump cannot be appended to, which is why the whole file is rewritten rather than dated copies piling up. `make db-backup-schedule` installs `scripts/systemd/chessgod-backup.{service,timer}` as `systemd --user` units (daily 04:30, `Persistent=true` so a missed night runs at the next boot; the first run fires on install). Both the service and the script take a lock, because the timer and a hand-run `make db-backup` sharing the temp file left one of them with nothing to move. `BACKUP_COPY_DIR` in `.env` keeps a copy on an external or synced folder; nothing takes it off the machine otherwise. `make db-restore` was verified by restoring into a scratch database (same counts as live, 47s).

Running a single backend test file:
```bash
cd backend && .venv/bin/pytest tests/test_game_ingest.py
```

Running a single frontend test file:
```bash
cd frontend && vp test src/lib/chess-utils.test.ts
```

Backend dev setup (first time):
```bash
cd backend && python3 -m venv .venv && .venv/bin/pip install -e .[dev]
```

Frontend dev setup (first time):
```bash
cd frontend && vp install
```

## Architecture

ChessGod is a chess analysis and repertoire tool. Users import games from Chess.com, explore their opening tree, compare against Lichess master theory, and run Stockfish analysis in the browser.

### Backend (`backend/`)

- **FastAPI** app at `app/main.py` with `uvicorn`; all routes mounted under `/api`.
- **SQLAlchemy async** (`asyncpg` driver) + **Alembic** migrations (`alembic/versions/`). The Docker container runs `alembic upgrade head` on start — every schema change needs a migration.
- **Routers** (`app/routers/`): `import_games`, `games`, `tree`, `theory`, `analysis`, `health`.
- **Services** (`app/services/`): business logic lives here. Key ones:
  - `master_openings.py` — seeds ECO opening names from bundled TSV files and periodically syncs position stats from the Lichess Opening Explorer.
  - `theory.py` + `LichessExplorerClient` — fetches and caches Lichess master data.
  - `tree_builder.py` — builds the opening tree from imported games.
  - `game_ingest.py` / `pgn_parser.py` — parses and stores Chess.com PGN imports.
  - `import_cache.py` — caches fetched monthly archives so re-imports reuse already-fetched data; bypass with `?force=true`.
  - `observability.py` — in-memory request metrics store, protected by an admin passphrase.
- **Background task**: `maintain_master_openings()` runs in a `asyncio.create_task` loop on startup, seeding/refreshing master data every `LICHESS_SYNC_INTERVAL_HOURS` (default 6). Each run is uncapped by default and syncs positions that already have stored evaluations first.
- **Server-side analysis is a throttled background crawler, not a service that competes for the machine.** The old native-Stockfish `analysis-worker` was removed because it ate the host. `scripts/engine/crawl.mjs` replaces it on different terms: it loads the *same* `sf_19` wasm build and pinned net the browser does, so its rows satisfy the engine contract honestly rather than being a second engine's opinion, and it yields the machine rather than competing for it — `nice -n 19`, a rest between positions, and a pool that sizes itself to the machine. **The outermost control is presence, not load** (`scripts/engine/presence.mjs`). Load average and CPU pressure are both *reactive*: they only rise once the crawler is already competing with the person at the keyboard, so relief always arrives after they have felt it — reacting faster has diminishing returns, because the surge is caused by the pool growing while someone is present and the answer is not to grow then. Presence is therefore measured directly: `/proc/stat` is host-wide even inside the container and the container's own cgroup reports exactly what we used, so **other people's CPU = machine busy − ours**, in cores, over a 2s sample. Measured here: **0.07-0.20 cores quiet against 1.36-1.94 while the machine's owner was working** — an order of magnitude apart, and readable in two seconds rather than loadavg's sixty. Above `CRAWL_ACTIVE_CORES` (now **1.0**, as a 6s mean — see below) the machine counts as in use and the pool is capped at `CRAWL_ACTIVE_MAX` (**1**), and the full pool unlocks after `CRAWL_IDLE_AFTER_MS` (10min) of quiet. **Our own backend is not a person, and for days it was read as one.** Other people's CPU is machine busy minus *this container*, so the backend and Postgres count as somebody else; a queue pool rebuild costs **4.8 core-seconds over ~3s (1.67 cores)**, the pool expired every 600s and one busy sample holds "in use" for exactly 600s — so the crawler's own request kept the machine "in use" every hour of a measured day, 04:00-07:00 local included, at one engine under the 80C attended line, standing down for heat **39%** of the time (557 positions/hour). `createOwnWork` (`presence.mjs`) wraps the queue fetch, the upload and the health probe, and a sample whose window overlaps one of them is dropped like an unmeasurable one. Presence transitions are now logged (`machine in use (...)` / `machine quiet for 10min`), since the state both the pool ceiling and the thermal line hang on was invisible in the log. **The quiet baseline has also moved, so the line moved with it.** 0.5 was chosen against a box idling at 0.07-0.20 cores; measured per process it now idles at **0.45-0.6** (qBittorrent 0.25, GNOME Shell 0.09, another project's Docker dev stack 0.06, the rest ~0.1) with one-sample spikes past a core, so a single 2s sample over 0.5 could never go quiet. Somebody working holds 1.36-1.94 cores, and a coding agent's job (an `fplai update`, measured) about a core on top of the floor. `createActivityWindow` averages `CRAWL_ACTIVE_WINDOW` (3) samples against `CRAWL_ACTIVE_CORES` **1.0**, set in `docker-compose.yml` as well, so it takes `make crawl-recreate`. This was chosen from a trace taken while the machine *was* in use; the transition log is what confirms the unattended side, so read it after a night before moving the line again. **The active cap is chosen by measurement, not by caution.** Benchmarked on this box against a fixed single-threaded foreground workload and a 10ms timer (the jitter a video call actually cares about), while the pool searched real library positions — foreground best-of-5, jitter percentiles over 600 ticks:

| engines | foreground | vs idle | jitter p99 | jitter max |
|---|---|---|---|---|
| 0 | 153ms | — | 0.34ms | 0.61ms |
| **1** | 161ms | **+5%** | 0.42ms | 0.61ms |
| 2 | 179ms | +17% | 0.77ms | 2.59ms |
| 3 | 175ms | +14% | 0.28ms | 3.45ms |
| 5 | 227ms | **+48%** | 2.04ms | 4.05ms |

**One engine is free** — +5% is inside the run-to-run spread and the jitter percentiles are identical to an idle machine — so `CRAWL_ACTIVE_MAX` is **1**, not 0. **Five is what makes the machine feel slow**: everything in the foreground takes half as long again. That is the whole cost, and it lives entirely in the difference between one engine and the rest. Two earlier guesses at this were wrong in opposite directions and both were guesses: that one engine was harmless *because* of `nice` (it is harmless, but `nice` is not why — it does nothing for cache or memory bandwidth), and then that one engine was still too much (it is not; measuring it showed no effect at either metric). Note also that scheduling jitter stays under ~4ms even at five engines, so multi-second stalls were never jitter — they were throughput, plus the 2.2GB of RAM a five-engine pool holds. Re-measure with the two harnesses rather than reasoning about it: a fixed CPU loop for throughput, a periodic timer for latency. Presence cuts **straight to the cap rather than halving**, on its own 2s clock, during a batch as well as between — there is no ramp-down to feel. Verified over 2.5min of real use: the pool held at 1 engine with **no growth events at all** and CPU pressure 0.03-1.37%, against 27% when the surge was reported. `parseProcStat`/`parseCgroupUsage` return **null**, never 0, on an unmeasurable machine, and a null sample leaves the previous belief alone — reading a gap as 0 would look like "nobody is here" and invite growth at exactly the wrong moment. The load and pressure rules below still run underneath as backstops. **The pool is a range, not a number** (`scripts/engine/pool.mjs`, `CRAWL_WORKERS_MIN` 1 / `CRAWL_WORKERS_MAX` 5): before every batch `targetWorkers` spends whatever is left of the `CRAWL_MAX_LOAD` budget (0.7/core) after *other* people's work, so an idle box gets filled, a busy one gets a single engine, and only a genuinely saturated one gets none. It replaced an all-or-nothing guard that ran a fixed three and then stopped dead at the cliff — which both wasted an idle machine and was rude right up to the edge. The subtraction of our *own* load is what makes this safe: load average counts our engines, so without it a bigger pool reads as a busier machine and throttles itself. It discounts the **largest pool run inside the last minute** (`createLoadHistory`), not the one running now, because loadavg is a one-minute average and lags a resize — subtract the new smaller size right after shrinking and our own decaying load looks like someone else's, ratcheting the pool down and pinning it there. Throughput comes from **more engines, not more threads** — positions are independent, while Stockfish's parallel search shares a tree and scales badly. Re-measured over 86 real library positions at depth 22, each config in a fresh process after a warm-up, in positions/min: one engine 13.3, two 28.3, three 39.2, four 48.3, **five 54.4**, six 51.4; against 2 threads on one engine 21.8 and 4 threads 12.8. **Five is the knee on this box** (4 physical cores, 8 logical), and 8 cores × 0.7 lands on exactly that. An earlier note put the knee at three and said a fourth "buys nothing"; that measurement was taken inside a container capped at **2.0 cores** and was measuring the cap, not the engine — nothing above two cores of demand could have shown a difference. **A cgroup limit is not applied by `docker compose restart`**, which reuses the existing container: the crawler ran a 3-engine pool inside a stale 2.0-core cap for a whole crawl, throttled in **77% of all scheduling periods** (368,909 of 480,311), while the compose file said 3.5. Use `make crawl-recreate` for anything under `deploy.resources`; `make crawl-restart` only reloads code (`./scripts` is a bind mount). The compose service also **runs the crawler at `nice -n 19`**, which it did not do while the module docstring claimed it did (`NI` was 0 on the live process). That matters in the one-to-two minutes before a resize: loadavg is a one-minute average and the pool only resizes between batches, so the engines are still running when you first touch the machine — at nice 19 the kernel gives them only CPU nobody else wants, so interactive work preempts them immediately instead of waiting for the resize. Changing `command:` needs `make crawl-recreate`, like the resource limits. After recreating at 6 cores: `nr_throttled` 0, CPU ~496%, 2.3GiB of the 4g limit, and **53.3 positions/min sustained against 34.1 before (+56%)** — within 2% of what the five-engine bench predicted. Verified under synthetic load: at loadavg 6.71 the pool went 5→3, at 5.87 →2, then recovered 2→3→4→5 as the load cleared, storing 24-25 positions every batch throughout rather than standing down. **The pool shrinks at once but grows one engine at a time** (`nextWorkers`), and the wait between steps is counted in **wall-clock time** (`CRAWL_GROW_INTERVAL_MS`, 45s) as well as batches (`CRAWL_GROW_PATIENCE`, 2). Batches alone are not patience: a batch is only as long as the pool running it, so at one engine it is a handful of positions that can finish in seconds — the pool was measured going 1→2→3→4→5 in **fifty-one seconds, with three seconds between the first two steps**, and the machine's owner felt it as lag while a browser was open. The load average everything here is judged against is a one-minute average, so the gap has to be on that scale whatever the batch happens to be; it is 45.3s and 67.4s per step now. Moving straight to the target oscillates, and the oscillation is what a person at the keyboard feels: with a browser open the pool ran 3→5 at load 3.49, 5→4 at 5.75, stood down at 8.67, returned to 5 at 4.54, stood down again at 8.63, then 5→1 at 9.60 — a sawtooth that never settles, because five engines are themselves enough to produce the load that stands them down, and the moment they stop the load falls far enough to invite all five straight back. Growing a step at a time gives each added engine a full load-average window to show its cost, so the pool settles at a sustainable size while the machine is in use and still reaches the ceiling when it is not. **`nice` does not make this unnecessary**: it orders CPU *scheduling* and does nothing about the L3 cache and memory bandwidth five wasm engines saturate, which is exactly what a browser notices. **Batch size scales with the pool** (`ROUNDS_PER_BATCH`, `CRAWL_BATCH` is the batch a *full* pool takes) because the pool can only resize between batches: a flat 24 positions takes about ten minutes on one engine, so growing back to five took the best part of an hour and the crawler sat at one engine on an idle machine. Scaled, every batch runs ~25-30s whatever the size and the ramp 1→5 takes about 80 seconds. **A fast shrink rides on CPU pressure, not the load average** (`CRAWL_MAX_PRESSURE`, 20%): `/proc/pressure/cpu`'s `some avg10` is the share of the last ten seconds in which some task was runnable but waiting for a CPU, so it reacts in ~10s where loadavg needs ~60 — and that minute is exactly the window the person at the keyboard feels. It is read inside the container because `/proc/pressure` is not namespaced, it only ever *cuts* (pressure is a reason to yield, never to grow) and it cuts multiplicatively rather than one engine per batch. `parseCpuPressure` returns **null**, never 0, where PSI is unavailable — 0 would read as "measured, and idle" and let the rule fire on a machine that cannot measure it — and the load budget then governs alone. Measured here: five engines on an otherwise idle box sit at 0.75-1.7%, while the reading taken when the machine's owner reported real lag was **27%** — so the threshold is **10** (`CRAWL_MAX_PRESSURE`), clearly above idle noise and well below the painful end. It is also polled **during** a batch (`CRAWL_PRESSURE_POLL_MS`, 5s), not only between: at five engines a batch runs 30-60s, and between-batch checking makes that the whole reaction time a person experiences. Engines past the cut finish the position in hand and then stop taking new ones — never abandon a search, which does not stop the engine — and the cut carries into the next batch rather than being undone the instant the batch ends. It takes work from `/api/games/unanalyzed-fens` and uploads through `POST /api/analysis/evaluations`, exactly as the browser does, so it inherits the phase rotation, the clock-ordered post-opening queue, the per-position `fen_depths` targets and the upload dedup without duplicating any of it. It is built to survive a multi-day run unattended: a failed upload retries with backoff instead of counting toward the idle limit (that used to end a crawl for good after five tries, with exit code 0, so the restart policy would not revive it — and a backend restart is enough to trigger it), a stall waits itself out rather than exiting, and the container restarts `unless-stopped` so a crash, an OOM or a host reboot brings it back. `make system-audit` reports crawl freshness (`evidence_inventory.freshness`) because a stopped crawl leaves no error anywhere, just a coverage number that quietly stops moving. `make crawl USERNAME=name`, or the opt-in `crawl` compose profile (capped at `CRAWL_CPUS` cores and `CRAWL_MEMORY`, **6 and 4g** by default — the cap is a backstop against a bug, not the governor, so it must leave room for `CRAWL_WORKERS_MAX` engines plus Node or the cgroup throttles the pool the controller just grew and the two fight each other. Each engine is ~450MB measured, so five need ~2.8GB; the first version allowed 512m against a measured ~490MB, which risked an OOM kill mid-batch). Engines are created **lazily and then parked, never torn down** — the Stockfish build exposes no shutdown and `quit` aborts a wasm module — so shrinking just stops handing work to the tail of the pool, and a parked engine costs RAM but no CPU. That is why the ceiling is bounded by `CRAWL_MEMORY` rather than by the load budget. It takes the depth to fill to from the queue's own `review_depth` rather than picking one: guessing 18 while the browser filled at 22 put 69 positions four plies from their partners, past `MAX_PAIR_DEPTH_GAP`, so none of them could grade anything. Browser Stockfish 19 remains the other trusted source. `services/cloud_evals.py` is an optional external lookup helper, never a trusted learning source, and since migration 018 it writes to its own table.
- **Every other guard measures contention; heat is a separate cost channel, and `nice` does nothing about it.** Load average, CPU pressure and presence all answer "is something else waiting for a core?" A single `nice -n 19` engine contends with nobody, so on an idle machine they all read clean — PSI `full` at 0.00, other-cores near zero — while the package heat-soaks. `nice` orders *who* gets a core, never *how fast* it runs: on an otherwise idle box the engine holds a core at full boost, and on this i7-1165G7 (thin chassis, PL1 28W, no thermald) that is 88-91C sustained. Package throttling is not per-process and does not respect `nice`, so **every core drops, including the foreground work `nice 19` exists to protect** — measured at **82% of a 5s window throttled**, load 7.46, with the machine's owner reporting lag; 5.7 hours of accumulated package throttle over one 30-hour crawl. The protection was therefore *inverted*: the quieter the machine, the freer the crawler, the hotter the package, so by the time somebody sat down the chip was at 90C with no headroom and their first keystroke throttled. Note this does not contradict the `CRAWL_ACTIVE_MAX=1` bench above — one engine really is free in *scheduling* terms (+5%, jitter identical to idle) and is also entirely sufficient to hold the package at 88C forever. `scripts/engine/thermal.mjs` adds the missing guard: it reads `x86_pkg_temp` from `/sys/class/thermal` (not namespaced, visible in the container like `/proc/pressure`), stands the pool down **to zero** above `CRAWL_HOT_C` (85) until it recovers to `CRAWL_COOL_C` (80), and polls on the presence clock (5s) so it cuts **mid-batch** — a batch is 30-60s, long enough to reach the throttling band and hold it there. Zero rather than half, because heat is shed by leaving the cores alone, not by running a smaller pool, and at `ACTIVE_MAX` 1 there is no smaller pool anyway; recovery is 15-30s measured, which is what makes a full stand-down affordable. **It compares a 30s rolling mean, never an instant reading, and that distinction is the whole guard.** Judged instantaneously it starved the crawler to **0.00% CPU while 90% of the machine was idle**: re-measured with the crawler fully stopped and an ordinary desktop running, the package alone swings **64-90C, with 5 samples of 24 at or above the 85C trip, median 76C** — so an instant trip fires on somebody scrolling a page, and the original 75C floor was the *median* of that trace, a gate open half the time and slammed shut by the next render. What separates the crawler from the browser is not peak temperature but duration: a render spikes for seconds, a crawl soaks for minutes. Across that ambient trace **no 30s window averages above 83C**, while a crawling package holds 88-91C and averages straight through the trip. Measured end to end: **82% throttled at 136 pos/hour instantaneous → 10% throttled at 210 pos/hour windowed**. Raise `CRAWL_HOT_C` to trade machine responsiveness back for crawl speed; on a desktop with real cooling it costs nothing because the threshold is never reached. `deploy.resources.limits.cpus` is **not** the lever here — it is a backstop against a bug, and capping it to 0.6 measured *worse* (100 pos/hour) because it throttles the engine without touching the ambient heat that trips the guard.
- **Recovery is judged on a short window, the trip on the long one, and the asymmetry is the whole point.** The 30s mean exists to survive a *false hot*: this package spikes past 85C when somebody scrolls a page, and one spike must not stand the crawler down. Nothing produces a false cool — a package reading 60C is cool — so charging recovery the same 30 samples only means the window has to flush every hot reading before the pool may restart. Measured: the package falls from **85C to 66C within two seconds** of the pool stopping, and the crawler then idled at **55-62C, 20C below its own recovery threshold**, for about twenty seconds of every cycle. `CRAWL_COOL_WINDOW` (2, a 10s mean against the trip's 30s) reads recovery instead; reheating takes ~14s, which is its own hysteresis, so this cannot flap. **`CRAWL_RECHECK_MS` (2s) is the other half**: `waitForCapacity` re-checked on `CRAWL_BUSY_MS`, which is a *queue-outage backoff* (30s) and has nothing to do with how fast a package cools, so a crawler that was already cool and free waited an average of fifteen more seconds to notice. Resume latency went from 20-30s to **1-3s**, and the duty cycle from ~42% to ~85%.
- **Presence moves the thermal line, it does not merely cap the pool.** 85C is the right *unattended* trip — throttling starts around 83-85C on this box, so it sits as close to the hardware's own limit as it can get — but it is the wrong number to hand a person. Running continuously instead of cycling means the package *sits* at 85C, so somebody arriving finds no headroom at all, and the trip is a 30s mean so the crawler would take up to half a minute to get out of their way. `CRAWL_HOT_ACTIVE_C` / `CRAWL_COOL_ACTIVE_C` (80/75) apply while `machineInUse()` is true. Because presence is sampled every 2s, the threshold *drops underneath a package that is already over it*, so the pool stands down on the next poll rather than waiting out the mean. 80C sits above this machine's quiet band (54-60C idle, ~65-70C reading) and below the 83C its ambient trace reaches under real work.
- **The thermal ceiling has a warm band between "fine" and "stop": hold, do not grow.** It used to go straight from 0 to the full pool, and on a thermally limited box that sawtooths — the moment the guard releases, the load budget sees seven idle cores and grows, the pool reaches two, heats twice as fast, trips, stands down to zero and comes back to one. That is the same sawtooth `nextWorkers` grows one engine at a time to avoid, arriving by a different road. One nice-19 engine alone holds this package at **83-86C against a 54-60C idle**, so the headroom for a second does not exist. Above `coolC` but below the trip, `thermalCeiling` returns `max(min, active)`: work already running is never cut, a recovered pool still gets its first engine, and growth is what gets held. A genuinely cool machine (a desktop with real cooling, whose mean never reaches `coolC`) never enters the band and fills exactly as before. The mid-batch cut passes `liveLimit` as `active` for the same reason — only `hot` may cut a batch, and it cuts to zero.
- **Measured end to end, the four changes above took the crawl from ~315 to 598 positions/hour (+90%) while leaving the machine cooler.** Baseline was 24 hours of DB rows at 280-370/hour (overnight idle ~330); after, 120 rows in 722s of a quiet machine. Over that window: crawl duty **72%** of wall clock at 0.63 cores average, Postgres **0.15**, backend 0.01, everything else 0.07; package **76.7C average, 86C peak**; package throttling **3.3%** of wall clock. The package average falling while throughput nearly doubled is the whole point — the old cycle spent its time either at 85C or wastefully cold at 55-62C, and most of the heat was never the engine's. The pool held at **1 engine throughout, cycling 0↔1 thirty times in thirteen minutes** on the thermal clock, never growing toward 5, which is the warm band and the thermal reality of this chassis agreeing.
- **`GET /api/games/unanalyzed-fens` builds its work once and reuses it: ~63ms a request against 1.65-3.1s.** Two findings, measured on the live library. (1) The walk was mostly phantoms: the SQL work predicate counts any side searched past the review band as work even when its partner was searched just as deep (the starting position and its first replies at depth 34), so a 199-pair walk held **15** pairs with real work and 184 that `_pair_work` then discarded — the walk paged the whole library to fill its target with nothing. Every exact SQL fix measured slower (scalar `max()` 2.3s, grouped join 3.3s, anti-join 32s); instead each page's pairs get one small depth lookup (`load_depths`) and phantoms are dropped *before* they count toward the target. The walk now holds 182 real pairs of 183, and **75 middlegame** pairs against 26-50 before. (2) Between batches the work barely changes — only the positions just searched drop off — so the pool is cached (`queue-pool:v2:*`, `_POOL_TTL_SECONDS` **3600** — see (4)) and each request re-checks only its own pairs' depths, rebuilding when fewer than `limit × _POOL_REFILL_FACTOR` have work; imports clear it. Two earlier shortcuts stay reverted: filling an era from overflow after 96 games dropped middlegame work to zero. (3) **Dropping phantoms after the read was not enough, and it starved a one-engine crawl for thirty hours.** Each page was read once, taking `per_phase` rows per phase, and the rows Python then dropped — phantoms, plus the same opening decision repeated from other games — had already used up the opening's share, so the work behind them in the page was never read. A walk aiming for 200 pairs came back with **11**, and all of them touched the 13 positions the crawler had timed out on and excluded. The exclusions were applied to the finished pool, so `limit=5` (one engine) got `[]` every minute while `limit=10` got 8 and a plain GET got 500. Now `seen_pairs` counts each `(parent, child)` once and leaves it out of every later read (`tuple_(...).not_in`), a page is re-read with a doubling window until no phase fills its share, and exclusions filter the walk in SQL, with the pool keyed on their digest. Live library, cold: 200 distinct pairs in 2.5-3.1s, against 11 in 2.1-4.0s. `test_excluded_positions_do_not_empty_the_queue` and its two neighbours pin this. On the crawler's side, a timed-out position is set aside **with a backoff, not for the life of the process** (`scripts/engine/setaside.mjs`: 6h doubling to 48h, `CRAWL_RETRY_UNFINISHED_MS` / `_MAX_MS`), and `nothing queued` says how many are held back and when the next one returns, so an empty queue with positions set aside no longer reads like a finished library. (4) **A rebuild is only as fast as the machine it runs on, so it must not sit in the crawler's path.** The request that finds the pool expired rebuilds it inline: 2.5-3.1s on a quiet box, 5.3-5.6s at load ~8, and **44.5s** once at load 11.7 — the same pair reads that take 0.1-0.3s each stalled at 4-6s while another project's batch job, qBittorrent and 5GB of swap competed for the machine. Every surface of the rebuild was checked before blaming the queue code: EXPLAIN on a slow read showed no plan change, and passing the seen pairs as a hashed bigint key or not at all measured no better (no exclusion tripled the reads). With the crawler's shared 30s timeout that became **six queue timeouts in one night**, each followed by 2-4 minutes of backoff. The pool now lives an hour (each request re-checks its pairs' depths and imports clear it, so the TTL only guards work studied into existence on the board), and the crawler gives the queue request `CRAWL_QUEUE_TIMEOUT_MS` (120s) rather than the default 30s, because a slow answer from a healthy backend is still an answer.

- **A nearly analysed library must not make every queue request walk it.** At 99.4% coverage every pool is short of `limit × _POOL_REFILL_FACTOR` pairs with work, so the refill rule rebuilt the pool on every crawler request: 145 of 166 requests in a day took 3-10s (three ~90s), ~2,580s of the 2,700s of logged request time over three days, against ~63ms reused. A short pool is now rebuilt at most once per `_POOL_SHORT_REST_SECONDS` (900s; the marker `…:rebuilt` lives under the pool's prefix so imports drop it), measured live at 33s once then 0.18s. On the crawler's side `scripts/engine/idle.mjs` doubles the "nothing queued" wait from `CRAWL_IDLE_MS` (60s) to `CRAWL_IDLE_MAX_MS` (30min) while the queue's counts stay the same, and starts over when they move.
- **Resource settings measured in October 2026** (three research passes over the backend, frontend and stack): Postgres runs `jit=off` (the repertoire query spent 3.2s compiling against 1.3-1.7s to run) and `work_mem=16MB` (52GB of temp-file spills in four days at 4MB); Redis is a pure cache with no snapshots and `/data` on tmpfs; health checks run every 30s once up (`start_interval` keeps start-up fast) instead of spawning a process every 5-10s; the memory caps the containers had been given by hand (Postgres 1g, backend 768m, Redis 256m) are written in `docker-compose.yml` so a recreate keeps them. **Raising `work_mem` needs `shm_size` with it**: parallel hash joins live in `/dev/shm`, Docker gives a container 64MB, and at 16MB work_mem large parallel queries failed with "could not resize shared memory segment … No space left on device" (9 times in 8h) until Postgres got `shm_size: 256m`. A healthy `/api/health` is no longer stored as an event (it was 72-86% of all stored request rows), and expired events are purged daily in one `DELETE` (the purge used to run only when the admin panel was opened, so nothing was ever deleted). The bundled opening book is seeded once per process rather than on every wake of the sync loop, and `lichess_sync_min_position_games` defaults to **2**: positions seen in one game found master games 1.2% of the time (164k fetched) against 37.5% at two games, and the 2.4M one-off positions kept the sync running around the clock; one-off positions are still fetched on demand. The biggest drain measured on the laptop was not this project at all: another project's ~40 containers held the load average at 26-59 with 8GB of swap in use.
- **A fallback read must not be emptied by positions nobody can store.** With the pairs done, the queue's two fallbacks (newest unanalysed positions, then most recurrent) each read one window of `limit × 4` rows and dropped unstorable ones afterwards. This library's newest unanalysed positions are its 27 Chess960 games (1,075 positions the evaluations endpoint rejects), so a crawler asking for 5 read 20 of them and was told "nothing queued" all night while depth-22 work waited behind them. `fill_from` now reads in growing windows (`_FALLBACK_READS`, 6) until the batch is full or the source runs out; `test_unstorable_positions_cannot_hide_the_work_behind_them` fails without it. Chess960 games themselves are now out of the queue's scope (`standard_rules_condition`, `services/game_scope.py`, keyed on Chess.com's `[Variant "Chess960"]` header; other set-up positions are ordinary chess and stay in): "missing" went from 895 to 119 positions, all of them work the crawler can do.
- **The Node crawler asks for pairs at the review depth** (`shallow_pairs=true`, `review_band` in `_pair_work`). A side studied on the board at 30-34 made its partner a depth-34 job; one nice-19 engine never finished those, set them aside for 6-48h and came back to time out again, and they were the last work the queue had. Rows are stored per depth, so the crawler instead searches the studied side once more at 22, the row lands beside the 34 and the pair is graded at 22 like the rest of the library; `load_depths` reports a position's in-band depth when it has one so the pair then reads as done. The browser crawl never sends it: its depth-max cache would discard the shallower search, which is why the default still brings pairs to their deepest side.
- **A crawler without a backend is not a slow crawler, it is a stopped one — so the stack keeps it honest, and the log says so.** The crawler's only source of work is `GET /api/games/unanalyzed-fens` and its only destination is `POST /api/analysis/evaluations`; with the backend gone it has nothing to do and nowhere to put it. That ran for **35 hours**: the stack was stopped, the opt-in `crawl` profile was not, `restart: unless-stopped` kept the empty loop alive, and the container still reported `Up` while coverage sat frozen at 45.91% and `analysis_results` took its last row at the second the backend died. Nothing was lost — every searched batch had already been uploaded, and the one evaluation caught mid-flight stayed queued — but a day and a half of machine time was. Four changes, because each one covers a different way in: `backend` has a **healthcheck** (`python3` is the only HTTP client in that image) and `crawl` depends on it with `condition: service_healthy`, so starting a crawler starts a *healthy* backend rather than sitting next to a dead one; `postgres`, `redis` and `backend` restart `unless-stopped` like the crawler already did, so a crash or a reboot heals itself; **`make down` passes `--profile crawl`**, because a stack stop that leaves the crawler behind is exactly how this happened (naming a profile that is not running is a no-op); and `CRAWL_USERNAME` lives in **`.env`**, not in whichever shell started the container — a `make crawl-recreate` without it exits 2 and restart-loops, which is how the fix itself first failed. On the crawler's side `scripts/engine/outage.mjs` replaces a line that read `queue unavailable (fetch failed); retrying` every 35 seconds, unchanged, about 3,600 times. It **backs the retry off geometrically** to `CRAWL_QUEUE_RETRY_MAX_MS` (5min, from `BUSY_MS`), so a long outage costs a request every few minutes rather than every 35 seconds; it **probes `/api/health` and names the culprit**, since "fetch failed" alone sent nobody to the backend — an HTTP answer of any status means something is listening, so only a refused connection, a DNS failure or a timeout reads as `down`, and a probe that could not run reports `unknown` rather than accusing a backend that is fine; and it **logs the recovery**, so the log states the outage instead of merely repeating during it. It still never exits: waiting one out is the point, and exiting would restart-loop under `unless-stopped`. `make system-audit`'s `evidence_inventory.freshness` remains the other half — a stopped crawl leaves no error anywhere, just a number that stops moving.
- **An abandoned search does not stop the engine, and its output will be stored against the wrong position.** `analyse` used to reject on a timer and move on; the search kept running, and its `bestmove` arrived while the *next* position was being searched, so that position was uploaded with another position's evaluation. Nothing looks wrong — the numbers are real, just attached to the wrong board. Seen in the wild: one timeout at depth 34 poisoned every later search on that engine, `POST /api/analysis/evaluations` started refusing the batch ("The principal variation contains an illegal move"), and the crawl retried the same unacceptable payload 97 times over seven hours. Two defences now: `analyse` sends `stop` and waits for the `bestmove` that proves the engine is idle before rejecting, and every search carries a generation tag so a straggler from an older one is ignored (`scripts/engine/sf19.timeout.test.mjs` drives the real engine to prove it). The schema validator is what caught this — it refused every corrupt row, so none reached the database. A 4xx from the upload is a verdict on those bytes, so `requestJson` marks 400/413/422 `permanent` and the batch is discarded rather than retried forever.
- **`scripts/engine/` drives the browser's own Stockfish build from Node, for offline measurement only.** "No server-side engine" is a statement about CPU budget — the host cannot crawl a library in the background — not about being unable to start the engine. Some questions can only be answered by searching real positions (does a shallow search predict a deep one? does the clock predict a mistake?), and answering them with a *different* engine would measure the wrong thing. `sf19.mjs` loads `frontend/public/stockfish/sf_19.{js,wasm}` and the pinned net directly, so an experiment uses exactly the build whose numbers get stored. `make triage-measure SAMPLE=...` runs one. This must not become a background analysis loop.
- **Evaluations are stored per searched depth, and a move is graded only across depths it shares.** `analysis_results` is unique on `(position_id, engine, multipv_rank, depth)` (migration `017_analysis_depth_rows`, reversing 005's "deepest wins" collapse). An evaluation loss is the *difference* between two searches, so reading each position's deepest row and subtracting charges the gap between two searches to the player: a parent left at depth 30 by someone studying it on the board, differenced against a child the crawl left at 22, is a mistake that never happened. `MAX_PAIR_DEPTH_GAP` (`app/engine_contract.py`, 2 — Stockfish reports the depth it finished on, so a run asked for 22 can store 23) is the tolerance. Every surface that differences two positions applies it: `_CANDIDATES_SQL`, `_TREND_ROWS_SQL` and `_COVERAGE_SQL` (`services/improvement.py`) and `_MISTAKES_SQL` (`services/mistakes.py`). Each one picks **one measurement per decision** — closest-matched depths, then deepest — and only *then* judges whether the move was a mistake, so a shallower pair cannot win the decision by looking more like one. `GET /api/games/unanalyzed-fens` closes the loop: a pair with one side outside the review-depth band is re-queued on **both** sides (`_pair_work` in `routers/games.py`), so the shallower side is deepened instead of the pair staying ungradeable forever. Coverage counts gradeable decisions, so a deep-only side reads as not yet analyzed.
- **Centipawns are capped at `DECISIVE_CP` (1,500, `app/engine_contract.py`) before any learning query differences them.** Stockfish reports tablebase-backed wins as 8,000-20,000cp, so a king move from one to a draw read as "lost 80.4 pawns", and because candidates are ranked by the drop and the pool is cut at `_CANDIDATE_SCAN_LIMIT`, those endgames led the pool (132 of the first 1,000 were over 2,000cp) and dominated the ranking evaluation's loss sums. The cap sits below the mate scale (1,800-1,990) so a mate still outranks any score. Nothing is filtered out: **a mistake is kept however the game or the position turned out** — the player asked for exactly that, so do not add a "still winning" or win-probability filter. Measured with `make ranking-eval`: mean lift **+10.4% -> +19.8%**, worst split **+0.6% -> +9.8%** (the metric's own loss unit is capped too, so part of that is a less noisy metric). Card explanations now show the evaluation before and after ("from +9.9 to +0.0") instead of a pawn count.
- **Count distinct decisions, never decision instances.** The coverage query counts one instance per game a decision occurred in, so a library reporting 4,077 "analyzed decisions" had **177 distinct** ones behind it and the drill pipeline — which groups candidates by position — found 23 mistakes. Any claim that a change improves coverage has to be measured in distinct decisions or it is measuring repetition. This is not hypothetical: the opening queue was ordered by recurrence on the strength of a batch going from +28 to +217 "gradeable decisions", and in distinct decisions the same batches unlocked **+10 either way**.
- **The queue rotates across eras of the player's history, not just the newest games.** A newest-first walk fills its candidate budget long before it reaches old games: measured after a crawl session, the current month held **379** distinct covered decisions against **19-42** for every earlier month. That skew is not merely unfair to old games, it makes the library untestable — scoring the drill ranking (`make ranking-eval`) and every "is this pattern getting better?" trend compares an older window against a recent one, so an empty older window means the answer is permanently "insufficient evidence". `_HISTORY_ERAS` (4) slices the player's date range and `collect_pairs` walks each slice in turn, newest first, with the last slice taking whatever the others left unspent. The page of games each walk reads is **adaptive** (`_GAME_CHUNK_START` 32, doubling to `_GAME_CHUNK_MAX`): the pair query joins every decision in the page and sorts the lot to keep the best ~96, so its cost tracks the page size almost exactly — 55.7ms for 250 games, 12.7ms for 50, 7.6ms for 25. Four eras on the old fixed 250-game page took the endpoint from 60ms to 140ms; starting small and doubling only when a page fails to fill its target brought it back while still covering every era. **Each page is also split by phase**: `_board_phase` computes opening/middlegame/endgame in SQL (mirroring `_COVERAGE_SQL`'s material count) and `ROW_NUMBER() OVER (PARTITION BY phase ...)` gives each an equal share, because taking the first N rows by ply yields the opening and early middlegame of the newest game and the phase rotation can only rotate between phases that have candidates — a 12-pair batch went from 1 endgame / 8 middlegame / 3 opening to **4 / 4 / 4**. The endpoint settles at ~88ms warm — so recent play is still covered first, but never to the exclusion of everything else.
- **The sitting just played jumps the rotation** (`_FRESH_WINDOW` 12h / `_FRESH_GAMES` 6 / `_FRESH_RECENT` 2 days in `routers/games.py`). The Habits coach reads the newest game with most of the player's moves judged, and the era rotation gave a fresh game the same share as any old one: the day it was built, the three games just played had 180 positions unsearched and none in the crawler's batch. When the newest game ended within two days, its sitting's decision pairs are served first (counted as `fresh` in `selected_decision_pairs_by_phase`) and the rotation fills the rest; an old library never triggers it. The read clears `seen_pairs` for itself, because the pool's walk has already marked those pairs as seen. Live after the change: 24 of 24 positions served came from the newest games.
- **The opening bucket is ordered by recency; recurrence was tried and reverted.** Openings repeat and nothing after them does (7,521 opening positions carry 91% of all 74,193 opening decisions, one occurring in 2,968; past ply 20 the mean is 1.01 and the max 3), so searching the most-repeated opening positions first looks obviously right. It is not. Besides buying no distinct decisions, it steers coverage into the player's own main lines, which are the positions they know: measured over the corpus it built, recurrence-ordered opening decisions were mistakes **4.7%** of the time against **21.0%** for the rest of the queue. A better opening signal — deviation from master theory, whose data is already stored — is open work and must be measured the same way before it is believed. If recurrence is ever reconsidered, count it per user and never from `positions.total_games`: that column counts every imported game by anyone, and one account held 25,191 games against another's 7,525.
- **Only the active engine contract may live in `analysis_results`, enforced by a CHECK constraint** (`ck_analysis_results_engine_contract`, migration `018_quarantine_foreign_evals`). Every learning query filters `engine='stockfish-19' AND engine_version='19'`, so a row from any other engine could never grade a decision — it only inflated the table and blurred what "analyzed" meant, and it was kept out of results solely by each query remembering to filter. The migration moved what was there into two archives and deleted nothing: Lichess rows to `cloud_evaluations` (a cache of somebody else's search, at a depth we did not choose — never a learning source, and now written there by `services/cloud_evals.py` instead), and the Stockfish 17.1 / unrecorded-build rows left by the removed server-side worker to `legacy_analysis_results`. On the first real corpus that moved 8,883 of 9,110 rows out of the planner's table; archiving rather than dropping keeps the trust decision reversible.
- **Past the opening the queue is ordered by the clock, and the signal points the opposite way to the usual assumption.** Positions do not repeat after ply 20 (mean 1.01 decisions each), so there is no recurrence to order by — but `game_positions.think_seconds` costs no engine time and says a great deal. Measured over 210 decisions from the real library at depth 22: moves played in under a second were mistakes 8% of the time, the broad middle 23–32%, and moves thought about for 15s or more **52.9%** of the time (41.2% were outright blunders). A snap move is usually forced; a long think marks a position the player found hard, which is where they err. `_phase_balanced_pair_fens` sorts the middlegame and endgame buckets by think time descending, which raised the median think time of queued post-opening decisions from 4.5s to 23.8s. Work cost still outranks it, unclocked decisions sort at the median (`_MEDIAN_THINK_SECONDS`) rather than last — a missing clock is not evidence the move was easy — and the opening keeps recency — recurrence was tried there and reverted, see above. Full numbers and the untaken shallow-triage trade: `docs/analysis-priority-findings.md`.
- **`make system-audit` reports evidence provenance, not just coverage.** Every learning query filters `engine='stockfish-19' AND engine_version='19'`, so rows from any earlier engine are inert — present in `analysis_results` and unreadable by the planner. On the first real corpus that was 8,840 of 9,049 rows (97.7%), which makes a 3.9% coverage number read as "nothing has been analyzed" when the truth is "the analysis exists under an engine the pipeline does not accept". `summarize_evidence_inventory` (`scripts/audit_system.py`) reports the split, plus the quarantined archive counts. It validates **every** row in the table rather than only contract rows: filtering there meant a corrupt row under another engine was invisible, and 16 such rows went unreported (both a centipawn and a mate score, or `(none)` as the best move). Inert rows are a limitation, not corruption, so they inform the report without failing the integrity gate.
- **Shared cache**: `services/cache.py` (`get_shared_cache()`) is a Redis-backed JSON cache (`REDIS_URL`, in-process dict fallback when unset — tests run without Redis). It backs the mistakes/repertoire/family-stats/coverage TTL caches and the cloud-eval negative cache. A `_cache_warmup_worker` loop in `main.py` re-warms these per imported username so first hits are never cold — **but only while somebody is actually using the app**.
- **A warm cache costs more than it saves when there is nobody to serve it, and this one was the largest single drag on the crawl.** The warmup loop's premise — "each pass is a no-op while the cached entries are fresh" — was never true. The shortest TTL it warms is **60s** (`_COVERAGE_TTL_SECONDS`, `_FAMILY_STATS_TTL_SECONDS`) and a pass sleeps 50s *after* finishing, so at a 12-15s pass the period is ~65s and those entries had **always just expired**. Every pass recomputed all of them in full, forever, for a browser nobody had open. Measured with the crawler **fully stopped** and the machine otherwise idle: the box sits at 0.09-0.23 cores and 54-60C, and every ~60s Postgres burns **0.8-1.6 cores for 10-15s**, taking the package from 55C to **82C** on its own — with package throttling spiking to **610ms per 2s sample (30%)**, far more than the nice-19 engine ever caused. It also poisoned two of the crawler's three guards, because none of that CPU is in the crawl container's cgroup: `otherCoresBetween` reported **1.0-1.8 cores of "somebody else's work"**, well over `CRAWL_ACTIVE_CORES` (0.5), so **the crawler read its own backend as a person at the keyboard** and pinned itself at one engine around the clock, and the thermal guard stood it down for heat it had not produced. The feedback loop closed on itself: stand-downs made batches tiny (1-5 positions), which made the per-batch queue fetch more frequent, which kept Postgres busy. `settings.cache_warmup_idle_after_seconds` (600s, matching `CRAWL_IDLE_AFTER_MS` so both agree on when nobody is here) now skips the pass when no *person* has asked for anything. What counts as a person is the point: `MACHINE_REQUEST_PREFIXES` excludes `/api/health` (the container healthcheck, every few seconds forever) and the crawler's own `/api/games/unanalyzed-fens` and `/api/analysis/evaluations`, or the warmup would keep itself alive on an empty desk. The timer is seeded with process start rather than `None`, so a restart mid-session keeps warming and only an unattended box falls quiet. The first person back pays one cold request, once. A skipped pass still records a `cache_warmup` background task with `skipped: idle`, so the panel says *why* it is not running instead of looking like a dead worker.
- **The drill plan is rebuilt cold almost every time it is read, so the rebuild itself has to be fast.** Every `POST /api/analysis/evaluations` invalidates the player's plan, and the crawler uploads about every forty seconds (46 in 30 minutes, measured), against a 120s cache TTL — so opening Review meant a cold build: **5.7s**, half SQL and half re-classifying ~1,500 unchanged decisions (`detect_motifs` alone computed ~25k SAN strings). Two fixes, output verified identical against the old code (same drills, patterns, trends): `classify_pattern` is `lru_cache`d — its inputs are scalars and `Pattern` is frozen all the way down, so an unchanged decision reuses its classification and a changed evaluation is a new key — and `build_improvement_plan` runs candidates, coverage, trends and the due-review read on their own pooled sessions at once. The due-review read runs unexcluded and drops the overlap in Python; if it hit `_CANDIDATE_SCAN_LIMIT` the exact sequential query still runs. **5.7s -> ~1.6s** after an upload. Uploads also no longer drop the queue's `coverage:v3` counts (`include_queue_counts=False`): a progress label with a one-minute TTL, which cost every crawler batch a ~270ms rescan. Imports still drop it.
- **The drill plan is served stale-while-revalidate** (`routers/improvement.py`). Even at ~1.6s the rebuild ran on nearly every visit, because every upload bumps the generation. The endpoint now keeps a fresh entry (keyed on that generation) and a last-known one (`improvement:planlast:*`, a day): a fresh hit is served, a stale read serves the last plan at once and starts **one** background rebuild. Measured: **3ms after an upload**, against 1.6s. Drill answers call `invalidate_plan`, which drops both, so the player's own progress is never served stale (progress is read live in the build, but the whole plan is cached now). `tests/test_plan_cache.py` pins all three behaviours.
- **Needs Work, Openings Health and Theory Deviations are stale-while-revalidate too** (`services/swr.py`, the plan's pattern made reusable). Each keeps a fresh copy under the evidence generation and a last-known copy without it; a stale read is served at once and starts one background rebuild. Measured with the fresh copies dropped: family stats **0.66s -> 7ms**, mistakes **0.70s -> 3ms**, deviations **0.50s -> 3ms** (deviations were not cached at all before, 0.19s warm). Keep the last-known key **outside** any prefix invalidated with `versioned_only=True` — the in-process fallback cache deletes local keys under the prefix either way. Imports still drop both copies where the data changed (`famstats:{user}:`, `deviations:`), so an import never serves pre-import counts.
- **Evidence uploads invalidate at most once per player per two minutes** (`_invalidate_for_upload`, `services/improvement.py`), with one trailing invalidation for anything that arrives inside the window, so the newest evidence still lands within it. Every crawler upload (about every 40s) used to drop all of the player's evidence caches, and the warmup — which runs while someone uses the app — rebuilt them on nearly every pass: **13.7s of Postgres a pass**, competing with the person it was warming for. The same pass no longer calls the analysis queue (it walked the whole library, ~1.5s, to warm a progress count the crawler refreshes anyway) and warms the plan through its served, stale-while-revalidate path. Cache lifetimes rose accordingly (family stats and repertoire 600s — imports and marks clear them; mistakes 600s and improvement coverage 300s — evidence bumps their generation; queue counts 300s).
- **`position_moves` needs its own autovacuum settings, or the master-move index is never index-only** (migration `020_master_order_covering`). The default threshold is 20% of 2.6M rows while a master sync rewrites ~40k, so the table was never vacuumed and the visibility map stayed unset; `idx_pm_master_order` now `INCLUDE`s `move_uci` and the table vacuums at 1%. The top-three master moves step of `_MISTAKES_SQL` went **497ms -> 20ms** and Needs Work **~1.4s -> ~0.7s** cold, same 206 rows.
- **The rating floor follows the player; it is not a fixed 1,000** (`player_rating_floor`, `services/game_scope.py`). Games below the floor are left out of the analysis queue, coverage and the drill plan, because they come from before the player could play. Fixed at 1,000 it did that for saint_uwe (1,942 of 4,217 rapid/blitz games are early sub-1,000 ones) and dropped **every** game of anyone rated under 1,000 — an 800 player's queue, coverage and drills were all empty, and the crawler (which passes no floor) had nothing to analyse. Omitted from a request, `min_user_rating` is now `min(1000, current rating − 200)` in whichever of rapid and blitz is lower, so everyone already past 1,000 is unchanged. The frontend no longer sends 1,000; it shows the floor the server reports.
- **`GET /api/improvement/where-points-go` answers "should I be studying openings?" from the player's own games** (`services/points_lost.py`). Loss is counted in *winning chances* (the expected-score curve Lichess uses for accuracy), not centipawns: summed centipawns rank won endgames as the weakest phase. Pairing follows the drill queries exactly (contract rows, `DECISIVE_CP`, folded mates, `MAX_PAIR_DEPTH_GAP`, one measurement per decision). Each phase's share is its average loss per analysed move times the moves the player *made* in it, so a library analysed mostly in one phase is not misread; with fewer than 200 analysed decisions on either side of move 10 the verdict is `insufficient` and the card says to analyse more instead of drawing bars. Measured on saint_uwe (87,844 decisions): moves 1-10 are **24% of moves and 19% of winning chances lost**, the middlegame 70%, the endgame 11%; **71% of everything lost comes from 1 move in 9**; after the opening, 54% of the loss is a capture or check allowed or missed. Opening theory is the wrong study for this player, and the 12 worst opening decisions together are ~6% of opening loss — so the card names only moves played 3+ times losing a pawn+ on average (Scotch 5...Nf6, 21 games, −2.2), never a repertoire. Served stale-while-revalidate (`improvement:losses:` is in `invalidate_improvement_caches`; the last-known copy lives outside it). ~1s cold for 90k decisions, 4.8s for hikaru's 17k games.
- **New games are fetched without being asked, while somebody is using the app** (`services/auto_sync.py`, `_auto_sync_worker` in `main.py`). The challenges, the repertoire check and "Are you improving?" are all measured from imported games, and the first player's library had stopped on 12 September: the last import had failed on a DNS blip ("Temporary failure in name resolution") and nothing retried it. The worker follows the warmup's presence rule (no interactive request in `cache_warmup_idle_after_seconds`, nothing fetched), syncs only players with an import job in the last 90 days or a training event in the last 30 (never hikaru's 25k games imported once to look at), at most every `AUTO_SYNC_INTERVAL_SECONDS` (3h; 0 turns it off) and 30 minutes after a failure. An import re-reads only the current and previous month's archives, so a sync is a handful of Chess.com requests. `run_import` now takes the HTTP client rather than the request and returns the new-game count (None on failure), so the worker can run it outside a request.
- **Settings** (`app/config.py`): `pydantic-settings` reading from `.env`. Notable knobs: `LICHESS_*` throttle/cooldown settings, `REDIS_URL`, `OBSERVABILITY_ADMIN_PASSPHRASE_SHA256`, `TREE_MAX_DEPTH`.

### Frontend (`frontend/`)

- **React 19** + **Vite+** + **TypeScript**. Path alias `@/` maps to `src/`.
- **State**: two Zustand stores — `app-store.ts` (global app state: FEN, username, filters, move tree, replay) and `engine-store.ts` (Stockfish lifecycle, analysis queue, cached results).
- **Routing**: no React Router; `App.tsx` checks `window.location.pathname` directly — `/admin-observability` shows the admin page, everything else shows `Dashboard`.
- **The Review tab is three views of one-page-at-a-time chips, not a stack of sections** (`workspace/review-panel.tsx`): Train / Progress / Reference at the top, then a chip per page, then exactly one page on screen — the player asked for this twice ("10 sub pages", "separate all them"), so do not re-stack it. `PAGES` is the single source of each page's id, view, label and caption; `SECTION_VIEWS` derives from it and `revealSection(id)` anywhere in the app switches view *and* page before scrolling, which is also why every linked page must stay in `PAGES` (pinned by `review-panel.test.tsx`). A page mounts only while shown, so its queries start on selection and stop on leaving; pages past Today and Blunder Check are also `lazy` chunks (main bundle 522KB → 450KB, 158 → 139KB gzip) behind one `Suspense` whose `PanelSkeleton` holds the page's space. A module imported eagerly anywhere else (as `week-scoresheet` is, by the Today card) stays in the main chunk, so check before expecting a split to shrink anything. View and per-view page choices persist in `localStorage`. **Starting a course session must navigate to the Course page** (`revealSection('review-course')` after `startSession`) — the session renders inside `OpeningCourse`, which is unmounted everywhere else, so a bare `startSession` is a button that visibly does nothing.
- **A list row that changes the board must show the move, not just the position.** Bare `pushPosition(fen)` hangs a SAN-less node off whatever is current: no last-move highlight, a blanked move list, and (from a stale parent) bogus classification badges. The rules, applied across Mistakes, Deviations, Points, Openings and Repertoire: a jump to a studied position is `loadPosition(fen, lastUci)` (roots the tree, highlights the arriving move); a click inside a **loaded game** (costly moves, the eval graph) is `jumpToFen(fen)`, which lands on the game's own node and only falls back to a branch for a position outside the line; and a row whose point is a move pair draws it with **position-scoped trainer arrows** — `setTrainerArrows(arrows, fen)` applies only while the board is on `fen` (compared on the first four FEN fields), so browse arrows can never trail the player onto another position, while trainers keep passing no fen and manage their own. Played move in `THREAT_ARROW_COLOR`, better move in `BEST_MOVE_ARROW_COLOR`; align the mover's side to the bottom (`alignBoardToUserColor`). `sanToUci` (`lib/chess-utils.ts`, memoized) rebuilds a UCI when the server only sent SAN.
- **Hooks** (`src/hooks/`): data-fetching and derived state live here (e.g., `use-opening-tree.ts`, `use-theory.ts`, `use-engine.ts`, `use-board-workspace.ts`).
- **API layer**: `src/lib/api.ts` (axios) + `src/lib/api-errors.ts`.
- **Engine**: Stockfish 19 (`sf_19`, the pinned single-net build) runs in a web worker (`src/lib/stockfish/`). Requires COOP/COEP headers (set in `vite.config.ts`). Assets come from `@lichess-org/stockfish-web` and are copied to `frontend/public/stockfish/` at `postinstall` / container start. Depth targets live in `store/engine-store.ts` (`DEFAULT_DEPTH`); parent and child positions must use the same depth or mistake detection can read phantom eval drops.
- **Theory revamp**: opening family hierarchy lives in `opening_families`, user intended-line marks in `repertoire_marks`, and browser Stockfish evaluations are batched back into `analysis_results` through `/api/analysis/evaluations`.
- **Client data cache**: API-backed frontend hooks use TanStack Query (`src/lib/query-client.ts`) for stale-time caching, request cancellation, and prefetch-friendly query keys.
- **Telemetry**: `src/lib/telemetry.ts` emits frontend events (errors, slow tasks, failed API calls) to the backend for the observability panel.
- **Dev proxy**: Vite proxies `/api` → `API_PROXY_TARGET` (default `http://localhost:18000`; compose sets `http://backend:8000`, because inside the container `localhost` is the frontend itself). The same options serve `vp preview`.
- **While the tunnel is down, chess.uwe.rw shows its own page, not Cloudflare's error 1033.** The zone is on the Free plan, where custom error pages are not available, so a Worker (`scripts/cloudflare/offline-worker.js`, deployed as `chessgod-offline` and routed on `chess.uwe.rw/*`) passes every request through to the tunnel and answers only a browser's page request (`Accept: text/html`) that comes back 502/503/504/52x/530 with its own 503 page: a board corner at dusk with the king laid on its side, "Adjourned · ChessGod is off the board", and a script that polls `/api/health` and reloads when the laptop is back. API and asset requests keep their real status, so the app's own outage screen still works once it is open. Verified by stopping `cloudflared` for 25s: page 503 with our title, API 530, page 200 again after. `make offline-page` redeploys it (needs `CLOUDFLARE_API_TOKEN` in `.env.tunnel`; the first deploy went through the Cloudflare connector). Workers are on the free tier (100k requests/day); the crawler talks to the backend directly, not through the tunnel.
- **Public deploy is `make tunnel` (Cloudflare tunnel to `chess.uwe.rw`), and two things broke it silently.** Vite refuses unknown `Host` headers, so the tunnelled hostname got **403 "Blocked request"** on every page until `allowedHosts` named it (`vite.config.ts`, extend with `ALLOWED_HOSTS`); and `--env-file .env.tunnel` *replaces* `.env` for interpolation, so the public stack ran with `LICHESS_API_TOKEN` empty — master theory blocked, no error. The Makefile passes both files now. Verify with `curl -H 'Host: chess.uwe.rw' localhost:15173/` (and `/api/health`) before starting the tunnel. The token itself lives only in `.env.tunnel`, never committed.
- **The compose stack serves the production build** (`FRONTEND_MODE=production`, the default: `vp build && vp preview`); `FRONTEND_MODE=dev make run` brings back the hot-reloading dev server. React in development mode was most of what made the app feel slow: stepping 40 moves through a 170-move game froze the main thread for **3.5s** on the dev server against **0.2s** on the build (0 with no other tabs running engines), and the workspace appeared in 0.6s against 0.3s. Measure performance on the build, never on `vp dev`.
- **What stepping through a game costs is pinned by caching, not by hoping React skips renders.** Profiled per step before the fixes (~115ms a step on the dev server): `buildReplayMoveAnnotations` re-graded every move on every step (now `measureMove`, keyed on the analysis objects via `WeakMap`, so a move is graded once per evaluation it depends on, and the brilliancy check counts material from the FEN instead of replaying with chess.js); the hanging-piece arrow regenerated every opponent move per render (`findOpponentHangingPieceThreat` memoised by FEN); `uciToSan` and `isLegalEngineMove` load a board per call (both `memoize`d, `lib/memo.ts`); live engine info lines were replayed move by move (now first move only — full lines are checked by `storableLines` when stored); `hydrateAnalysisCache` replayed every stored PV (~450ms on loading a 170-move game; server rows were already validated on upload, so it checks the first move); move buttons and the opening list re-rendered on every step (`memo` on plain props, `useStableCallback`); dates built a new `Intl` formatter per row (`lib/format-date.ts`). Profile with the CDP `Profiler` against the build before assuming where time goes.
- **Backend tests must never start the real app against the real database.** `tests/test_health.py` used `with TestClient(app)`, which ran the lifespan — master-theory sync against Lichess, cache warmup — and wrote its fake `unhandledrejection` / "frontend failure" event into the real `observability_events` table on every run: 209 fake errors had accumulated in the panel. It now uses a throwaway SQLite file and no lifespan. Cancelled requests (`ERR_CANCELED`, TanStack Query dropping a stale fetch) are no longer reported as `api_request_failed` either.
- **Frontend tests run with Node's own `localStorage` switched off** (`execArgv: ['--no-experimental-webstorage']` in `vite.config.ts`'s `test` block). Node 25+ ships an experimental `localStorage` global that is undefined until `--localstorage-file` is passed, and inside the jsdom environment it shadows jsdom's: after the bundled Node moved to 26, every jsdom test that touched the app store failed on `window.localStorage.getItem` (16 files) with nothing in the app changed. The app runs in a browser and never wants Node's copy.

### Reviewing a game (frontend)

The library-wide crawl in **Analysis Coverage** is a background chore — measured at ~10 positions/min in the browser, a 168k-position library is hundreds of hours. The usable unit is one game, and that is what the Review panel is for.

- **One depth for own-game analysis**: `GAME_REVIEW_DEPTH` (`lib/analysis/review-depth.ts`) is used by both the crawl and a single-game review. It is deliberately not the interactive depth selector — that defaults to 30, and a 120-ply game at depth 30 takes about fifty minutes. Both paths must stay on the same number or mistake detection differences a parent eval against a child eval at another depth and invents eval drops.
- **A review covers the whole game**, not the moves stepped through so far: `buildFullGameLine` (`lib/analysis/active-line.ts`) walks up to the root *and* down the main line. `buildActiveReplayLine` stops at the cursor, which is right for board markers and wrong for a review — a freshly loaded game sits at move one.
- **The game review is its own section (`explore-game-review`), not a child of "Engine".** Nesting it there meant collapsing Engine hid it completely, and "Review" collided with the Review tab, which holds lessons and stats instead. It is titled "Game review" and is one of Explore's pages. **Explore is pages too**, like Review (`workspace/explore-panel.tsx`: Game review · Engine · Play · Library · Position, one on screen): five stacked sections with three open were the same clutter. The engine auto-analyses **on the pages that read the board** (Game review, Engine, Position — `ENGINE_PAGES`) and rests on the Library, where every click loads a new position and nothing is read; the dashboard starts it off and the panel turns it off on unmount (a collapsed sidebar). Do not narrow it to the Engine page alone: trying an alternative off a reviewed game is the review's main use and needs live lines. A game starting against the engine switches to Play and its end switches to Game review; picking a game in the Library lands on its review; links in (`revealSection('explore-…')`) switch page, pinned by `explore-panel.test.tsx`. The caption under the chips carries the review's graded-moves count.
- **The starting position is never analysed automatically** (`lib/analysis/auto-analysis.ts`). The board sits at the initial position until a game or line is loaded, and `use-engine`'s effect fires on every `currentFen` change — so simply opening the app began a **depth-30 search of the opening position**, on load, before anything was chosen. It is the one board whose evaluation is a known constant, is identical for every user and every game, and belongs to no decision anybody made: the first move is an opening preference, not an error. `shouldAutoAnalyze` compares placement/side/castling/en-passant only, since the move counters are not what makes it the start. This governs the *automatic* search alone — pressing analyse, or stepping onto the position in a review, still works.
- **A finished review ends on a medal** (`.review-done` in `game-review-panel.tsx`): the gold magnifier, how many mistakes are left to try again, and the Retry button — or "Nothing to retry" for a clean game.
- **"Retry your mistakes" is Chess.com's Retry** (`components/analysis/retry-mistakes.tsx`, logic in `lib/analysis/retry.ts`). Once a review is complete, the player's Mistake/Blunder/Missed Win moves (the worst eight, asked in game order) are replayed from the position they were played in. Three rules: **snapshot the mistakes before starting** — an attempt branches off the game on the board, and `buildFullGameLine` from a variation node stops at it, so the review's own line (and its annotations) shrink the moment the player moves; **judge more than the first choice** — the review pool searches MultiPV 1, so an alternative is searched on its own (`RETRY_DEPTH` 16, the position before it at the same depth, so the two are comparable) and counts if it loses under 5% winning chances; replaying the game move is caught first and never counts. While a position is asked, `drillSolving` hides the eval bar, the engine lines and board hints and stops auto-analysis (the search of the asked position *is* its answer) — which also fixes drills showing the evaluation. `useReviewReward` is skipped during a retry, since the shortened line would otherwise hash as a new reviewed game. `retry_found` / `retry_missed` are client events like the quiz, deduplicated per game and ply; badge "Second chance" at 25.
- `useAnalyzeLine` is the single entry point for starting a run; the rail button and the Review panel's own button both call it.
- **A game review runs on a pool of single-threaded engines, and the main engine uses two threads — both measured in Chrome, not assumed.** More threads make this wasm build *slower* to a given depth: 8 middlegame positions at depth 20 took 1.72s each on one thread, **1.08s on two**, 1.36s on three, 1.78s on four and 2.41s on seven — and seven (`cores − 1`) was the default, so every analysis in the app ran at a third of the speed it could. Node agrees in direction (depth 22: 3.43s one thread, 8.52s seven). Independent positions therefore go side by side: 4 engines × 1 thread reviewed at an effective **0.45s** a position against 1.08s for the best single engine. `queueReplayAnalysis` (the non-background path — one game's review) hands its positions to `runReviewPool` (`lib/stockfish/review-pool.ts`, `reviewPoolSize` = half the cores, at most 4) and results merge into the cache exactly as queued searches do; library batches (`background: true`) stay on the main queue. Pool engines are created per review and destroyed after, because each worker holds its own copy of the network (~1.9GB for four, measured). Measured on a real 75-position game, crawler running and the package at 89C: **depth 18 in 24.8s** (games against the engine, `QUICK_REVIEW_DEPTH`), depth 22 in 104s when nothing is cached — against ~9 minutes before. That worst case is rare: the 12 most recent library games had 0-10 positions each left to search, and a 170-move game opened fully reviewed in **1.0s** from hydrated server evaluations. Giving each engine a contiguous stretch of the game, searched backwards for hash reuse, measured *slower* (158s vs 113s, confounded by heat but no sign of a gain); the pool keeps handing out the next free position.
- **The review talks about the move on the board, the way Chess.com's does.** It used to list every costly move for both sides under a scoreline, which the player read as noise ("it should show info based on the current thing on the board"). `GameReviewPanel` now shows, per side, an accuracy figure (`sideAccuracy`: Lichess's winning-chances curve and move-accuracy formula over the evaluations either side of each move; a best move is 100) and a table of grade counts, the eval graph, and a `CurrentMove` card that follows the cursor: the grade icon, "16. Bxd4 is an inaccuracy", who played it, the cost, "Best was Nxd4" and the explanation line from `/api/analysis/explain` for that one move. The card has three fixed lines and one min-height, so stepping moves nothing; the move list's `.move-annotation` slot is always rendered (14px) so a grade arriving moves nothing either. **Brilliant is judged the way Chess.com judges it** (`isSacrifice`, `isBrilliantMove` in `replay-annotations.ts`): a piece sacrifice read on the board two plies deep — for every capture the opponent has, the piece taken against the cheapest recapture, with what the move itself captured subtracted, a loss of two pawns or more counts and a pawn never does — that is the engine's move or within 30cp of it, from a position under +500 into one not below −100. The earlier rule only looked at whether the engine's reply took the piece, so it missed every sacrifice the engine declines.
- **A review says why a move was bad, not only what it cost.** Each costly move shown carries one line from `POST /api/analysis/explain`, which runs the drills' own `classify_pattern` over the engine lines either side of the move (`explanationRequests`, `lib/analysis/move-explanations.ts`): the motif when there is one ("Skewer. Allowed: Qxe7 lines up the queen on g5 in front of the rook…"), else the capture that punished it ("Nxg5 wins the bishop"), else the pattern's cue. It is stateless and cheap (the classifier is `lru_cache`d), and the line's height is reserved so the words arriving never move the list. Which side played a move comes from the FEN after it, not ply parity — a position played out against the engine can start with Black to move.
- `useMoveAnnotations()` follows the board; `useMoveAnnotations(useGameLine())` grades the whole game.
- **The main engine starts on the first search and is given back after five idle minutes** (`ENGINE_IDLE_RELEASE_MS`, `touchEngine` / `releaseEngine` in `engine-store.ts`). Its worker holds ~450MB of wasm plus its hash (~0.95GB, ~1.45GB with the deeper search), and `useEngine` used to start it on mount and nothing ever released it, so it held that memory from page load until the tab closed, Review tab included; verified after the change that a page load fetches no Stockfish asset at all. "Idle" means no active or queued search, no game review on the pool, no pending debounce and no game against the engine in progress (the opponent's worker is needed between moves). Switching the engine off releases it at once. Two consequences: anything that waits for `isReady` must start the engine itself (`DrillContinuation` calls `init()`), and the debounce timers are set back to null when they fire — they were left set, which read as pending work forever and would have kept the worker alive. `engine-idle.test.ts` pins both release and the game-in-progress hold.
- **Engine state is read where it is shown.** `useEngine` subscribes to 17 fields, and the workspace root, the board and the rail each called it, so every line the engine reported (up to once a frame while searching) redrew the whole workspace and react-chessboard with it. The dashboard now calls `useAutoAnalysis` (the effects only, subscribed to the position and the switch), `EngineLines` reads its own lines through `useEngineView`, the board reads `enabled` / `toggle` / `isLoadingNnue` directly and the rail `activeMode` plus the plain `analyzeBoard` function. Keep new consumers on narrow selectors; `useEngine` is for the components that really show most of it (the engine bar).
- **The network file is hashed once, then trusted by a marker on its cached copy** (`x-chessgod-verified: <12-hex digest>:<byte length>`, `nnue.ts`). Hashing ~98MB cost 177-263ms of CPU on every engine start, the review pool starts four, and the main engine now restarts after its idle release. The marker is written only after the bytes matched the digest in the filename; a copy whose length or name no longer matches is hashed in full and replaced if bad, and a copy cached before the marker existed is marked the first time it verifies. The case it accepts: bytes corrupted in place with the same length, which Cache Storage's atomic writes make vanishingly rare.
- **Leaving the board stops the board search** (`stopInteractive` in `engine-store.ts`, called by `useEngine` when its caller's `autoAnalyze` goes from on to off). A depth-30 search ran on for up to its 90s timeout on two threads after the player left every surface that reads the board (the Library, the Review tab, a collapsed sidebar, a drill being solved). It drops interactive jobs only, keeps what the search reached (`interruptActive`, shared with the queue's own interrupt), and leaves a game review and the library crawl running. Only the on-to-off change counts, so callers that never auto-analyse cannot stop it.
- **Timers sleep when nothing changes.** The eval sync's 3s timer only flushes; it rescans the analysis cache (up to 5,000 entries) only when a pass stopped at `MAX_PENDING_ITEMS`, since every new result already arrives through the store subscription. Game clocks redraw at each second boundary (100ms only under ten seconds, where tenths show), and the flag is one timeout set for the moment the running clock reaches zero, re-armed on every clock change, instead of a 100ms poll. A hidden tab stops the board search only (`stopInteractive`): it used to call `stop()`, which also aborted a game review that then never restarted; the in-browser library crawl takes no new batch while the tab is hidden.
- **A deep look at the board that runs out of time keeps what it reached.** Interactive searches aim for depth 30 with a 90s position timeout; on this laptop (two threads, crawler running, hot package) they often stop around depth 26. The timeout used to log `engine_error` and discard the lines — six times in one session — so returning to the position searched from zero. It now completes the search with the lines it has (`startPositionTimeout`, `engine-timeout.test.ts`). Replay jobs keep the retry/defer policy.
- **Progress is always quantified.** `useAnalysisProgress` measures this run's rate and `formatDuration` turns it into a time. Long waits get an ETA rather than a spinner, and the coverage meter projects the same rate onto the whole library so the number is honest.
- **The crawl reports what the engine took, not what it was offered.** `queueReplayAnalysis` resolves with the number of positions actually enqueued; a position already cached at the requested depth, or one that is already checkmate, is not work. Counting the offered batch instead made `EngineAnalyzeBatch` re-request the same 24 FENs every 30s forever while the panel claimed to be analyzing. After `MAX_IDLE_BATCHES` cycles that queue nothing, the crawl stops and says the remaining positions are already analyzed here and waiting to upload.
- **`/api/games/unanalyzed-fens` returns `fen_depths`, and the crawl honours it per position.** A decision is graded by differencing its two positions, so each is searched to the depth its partner already carries rather than to one depth for the batch — a parent studied on the board at depth 30 makes its child a depth-30 job. The server never asks for a *shallower* re-search: `mergeEngineAnalysis` keeps the deeper line per rank, so a shallow result would be discarded by the browser's own cache and the pair would stay ungradeable forever. See `MAX_PAIR_DEPTH_GAP` in the backend notes.
- **Analysis coverage is shown per game phase** (`lib/analysis/phase-coverage.ts`, rendered in Analysis Coverage). The drill queue can only raise a mistake from a decision that was analysed, so a library judged 98% in the opening yields 98% opening lessons — and an empty middlegame queue reads as "no middlegame weaknesses" when the truth is that the middlegame was never examined. `describePhaseSkew` says so in those words. Measured on the first real corpus: 3,575 opening decisions against 26 middlegame and 40 endgame.
- `lib/analysis/game-review.ts` (scorelines, ACPL, costly moves) and `lib/analysis/eval-graph.ts` (curve geometry) are pure and tested; the components only render them.

### Drills (frontend)

- **"Where your points go" opens Review** (`components/improvement/where-points-go.tsx`, words from `lib/analysis/points-lost.ts`). It is for a player with little time: whether openings deserve any of it (compared with the opening's share of moves, not against nothing), the few repeated opening slips worth fixing — each loads its position on the board — and the one habit (checks and captures first) behind most of the rest. `shortOpeningName` trims the moves Chess.com appends to an opening name, which otherwise name moves that were never played in the position shown.
- **Every trainer has the same way out: "Explore this position"** (`ExploreButton`, `lib/explore-position.ts`). Blunder Check, the drills, the quiz, Retry and Rush offer it once the question is resolved; the line trainer always. It drops the question's rules on the board (`drillSolving`, trainer arrows, the hint square) and raises `OPEN_EXPLORE_EVENT`, which the dashboard answers by switching to Explore and revealing the Engine page, so the position stays and the engine's lines come up. The trainer itself unmounts with the Review tab and its own cleanup clears the rest; a course session survives in the training store, so returning to Review resumes it. Any new trainer gets this button rather than its own.
- A drill **jumps** to a position: `loadPosition(fen)` resets the move tree to a single root, so there is no parent node and nothing accumulates in the move list. Do not write copy promising that played moves appear there.
- Because of that reset, the board had no way to show the opponent's reply in a two-move drill — you were asked to answer a move you could not see. `loadPosition(fen, lastUci)` puts that move on the root node (`san` stays null, so it is never counted as played) and the normal last-move highlight picks it up. See `app-store.test.ts`.
- **A two-move drill has to say which move it is asking for.** `lib/drills/drill-steps.ts` derives the step (`Move 1 of 2` / `Move 2 of 2`), the answer for *that* step and the line with the asked ply marked. Everything the panel showed described the first move: the meta row read a flat "2 moves", and "Show hint & solution" from the follow-up state announced `card.best_move_san` — the move the reader had already found — because `setStatus('revealed')` does not record which step was being given up on. `askedStep` captures it. `drillStep` also refuses to index past a card with no `follow_up`, so a status left over from the previous card cannot read off the end.
- **`lib/drills/session-summary.ts` says what the training numbers mean.** The panel printed "113 positions · 114 times seen · 0% drill accuracy", where the first two look like the same quantity and the third does not say whether it comes from one wrong answer or a hundred. `describeCoverage` prints the occurrence count only when the theme actually repeats, `describeAccuracy` says what the percentage is a share of and never shows a rate with no attempts behind it, and `describeSessionEstimate` explains why a set stops at ten positions: `compose_session` fills a **600-second budget** (`_SESSION_SECONDS`) at `_SINGLE_MOVE_SECONDS` 40 / `_TWO_MOVE_SECONDS` 60 per card, so the limit is time, not a count.
- **A recommendation acted on is gone the moment it is done.** Every XP-earning write goes through `useApplyReward` (`hooks/use-training.ts`), which sets the profile from the reward and then calls `refreshTrainingQueries`: every query whose key starts with one of `training-repertoire`, `repertoire-check`, `training-challenges`, `improvement-plan`, `week-scoresheet` for the player is marked stale, so what is on screen refetches and the next page opened reads the state after the action (the player: "things that are recommended, then I go through them, should not be recommended again that instant"). A finished line also updates the cached repertoire at once (`status` new → learning, `due_moves` 0 for that line) before the refetch confirms it, so the Today card's next step moves on without waiting ~1.3s for the server. The drill themes' "Recommended" is `recommendedTheme` (`lib/drills/recommended.ts`): the first theme with positions ready that is not the one trained most recently today (`chessgod.drills.trainedToday` in `localStorage`); it used to be simply the first theme, which came straight back the moment a set in it ended. The attempt hook no longer invalidates the plan itself — the reward's refresh does — because both together cancelled and restarted the refetch.
- **The improvement chart shows when.** Its curve is games in order, not time, so `Trend` (`progress-card.tsx`) draws date ticks (first, last, up to three between, the year once the span crosses one), labels the training-start marker with its date, and the caption carries the span ("Sep 5 to Oct 21"); without them a week and a year looked the same.
- **The plan is fetched per theme, so `drills` is theme-scoped while `summary.due_positions` counts the whole library.** Reading an empty `drills` as "no lessons at all" told a user who had just finished one theme to go and analyse more games while seven lessons waited in others — and the header badge still said "7 ready" beside it. `getLessonAvailability` / `readyCountInView` (`lib/lesson-availability.ts`) decide both, so the badge always counts what the body is listing.
- **A finished drill shows what the engine says happens next** (`DrillContinuation`, `lib/analysis/continuation.ts`). The card names the move and explains why it is right, then stops — leaving the question the position actually raises ("and then what?") unanswered, and answerable only from the card's stored text. This is the engine's own line from the drill position, so it holds for continuations the card never wrote down. It is rooted at **the ply the drill asked about** — the follow-up position for a two-move card, not the opening one. Three rules: it renders only once the attempt is resolved (the continuation is the answer, so it must never appear while solving), it asks for a search only when the engine is **ready** rather than merely `enabled` — which is true by default, so asking earlier starts a search against a worker that does not exist — and it reserves its height, because the line lands when the search does. **The loading state is a row of move-sized pills, not the generic skeleton**: the box is itself `--surface-2`, so `PanelSkeleton`'s surface-2 → surface-3 shimmer vanished on it and "What follows" stood over an empty strip until the moves landed. `.drill-continuation__ply-skeleton` shimmers a shade darker than the box at the ply buttons' height, six pills wide, so the reader sees that moves are coming and nothing moves when they do. `pvToMoves` stops at the first move that will not play rather than throwing: a PV can outlive the position it was searched from, and half a line still reads. Evaluation is shown from the side to move, which is the person doing the drill. **Each ply is a button** that jumps the board onto that position (`loadPosition(fen, uci)`, so the move that led there gets the normal last-move highlight) and the ply the board is standing on is marked. That is safe only because the attempt is already resolved: the trainer's submit effect ignores every status but `solving`/`follow-up` **and** requires a node with a parent, while `loadPosition` roots the tree at a node without one — so exploring the line can never be graded as another attempt. Both guards are pinned by tests; check them before making the line reachable from a state that is still being solved.
- **The Opening Quiz asks the player's own positions against the master book** (`GET /api/theory/opening-quiz`, `services/opening_quiz.py`; `components/openings/opening-quiz.tsx`, first section under the trainer in Review). Positions are ones the player reached with the move theirs in the first 20 plies (`game_positions` row at ply *k* is the position after *k* plies and the move that led to it; ply 0 is the start and is never asked), with at least 100 master games; book is ≥3% of master games and ≥10 games. Positions where the player's *usual* move is off book come first — on the first real corpus that was 1.d4 d5 2.e3 (227 of 278 games, masters c4 77% / Nf3 18%) and 1.e4 e6 2.Nf3 (112 of 122, masters d4 90%). It reuses the drill mechanics: `loadPosition(fen, last_move_uci)`, the first move off that root is the answer, `drillSolving` hides book markers and arrows while asking. Only the first answer per position scores; "Try again" is practice. Cached stale-while-revalidate for an hour; imports drop it.
- **The drill card is the board's companion, not a form.** It read as one (the player's words: "too much text, scrolling things"): six "what did you check?" chips filled the card, the prompt explained the mechanics in a sentence, and the hint line landed under the buttons at the card's edge where nobody saw it. Now the clock and meta line, "Black to move." (plus "Two moves: yours, then the follow-up." only for a two-step card), the intents folded behind a "+ What did you check?" `<details>` (the server still records the one chosen), then the hint line — "Stuck? Take a hint." until a hint is taken — above a row of Hint and Show solution (`HintControl` with `lineFirst` and the solution button as its children). The scope note ("From your rapid and blitz games rated 1000+.") is a plain caption: an earlier layer had stripped its box on purpose and the tone-border rule must not put it back, so `.training-scope` is excluded from that rule.

### Training: the opening course and the game layer

The player asked for this in so many words: they know their openings hurt them, they have no time to learn theory, and they want the app to feel like something they *need* to come back to (Chessly/Chessable). Measured first, because the first answer given here was wrong: the "Where your points go" card said openings were fine because the first ten moves were 19% of the winning chances lost against 24% of moves — but it charged each loss to the move where the evaluation dropped, so an opening that hands over a bad position read as middlegame mistakes. **Measure what the opening delivers, by colour** (`out_of_opening`, `services/points_lost.py`): as White the player averaged +0.80 after move 10 and was a pawn down in 13% of games; as Black −1.06, a pawn down in **36%**, scoring **36%** in those games against 57% when level. Middlegame error rates were flat across every opening (15-18% big errors), so the White Italian was fine and the Black mirror of it was the leak.

- **The repertoire is built, not written** (`services/repertoire_builder.py`, `GET /api/training/repertoire`). It walks the positions the player actually reaches, follows what opponents *actually play against them* (≥5 games and ≥3% — the King's Gambit was 37 games but 5% of 1.e4 e5), and at each of the player's moves chooses: **keep** their move if it is within `KEEP_CP` (60) of the best; else **change** it to the sound (`SOUND_CP` 35) move masters play most; mark opponent replies that lose ≥150cp as **traps**. The two thresholds differ on purpose — every change is something to learn, and at 35 the Scotch fix became a new variation (4...Nf6 5.Nxc6 bxc6 6.e5 Qe7) where at 60 it is the one move that lost, 5...Qf6 for 5...Nf6 (−2.2 pawns, 40 games). The whole Black repertoire came to **18 moves to learn** across 59 lines. Past a change the line follows master replies for a few plies; transpositions that differ only in moves to keep are merged. Repertoire marks win when sound. A move with no evidence against it (outside the MultiPV lines, child never searched) is **kept as unchecked**, never replaced on a guess — and **an unchecked move is never preached or quizzed** (`expected_moves` and `rush_questions` in `services/training_games.py` skip `checked: false` steps, pinned by `test_unchecked_moves_are_never_quizzed_or_preached`): the repertoire check once told the player "your repertoire move is d4" off a single game with no search behind it, which is exactly the trust the surface cannot spend. The check and the weekly challenge treat the line as ending where the evidence ends; the step returns once `make repertoire-engine USERNAME=...` or the course's "Check now" has searched it.
- **Choices are compared inside one MultiPV search**, which the library did not have (64 positions of 156k had a second line). Unsearched positions come back in `needs_engine`; `make repertoire-engine USERNAME=...` (`scripts/engine/repertoire.mjs`, nice 19, one-off, `sf19.mjs` now takes `{ multiPV }`) or the course's "Check now" (the browser's `playMove`) searches them at MultiPV 4 and uploads through `POST /api/analysis/evaluations`, going round until nothing new appears (Black: 111, then 15, then 0). On this laptop run it with `ENGINES=1 DEPTH=18`: two engines at depth 20 held the package at 88C.
- **Per-move spaced repetition, MoveTrainer style** (`services/training.py`, `line_move_progress`, migration `022_training`): 4h, 1d, 3d, 1w, 2w, 1mo, 3mo, 6mo. Keyed by (FEN, move), so shared moves and transpositions are one memory. Correctness is decided on the server against the line, never taken from the client. **A line is `new` until every one of its moves has been taught** — they share 1...e5, and "any move known" turned lines never shown into ones to practise from memory. Reviewing before a move is due earns 1 XP and no climb, and the perfect-line bonus needs a due move: otherwise replaying a line farms XP. **Learned is not practised, and the course asks for the practice before the next line** (`recalls` on `line_move_progress`, migration `024_move_recalls`; `practised` / `recalled_moves` per line and `recalled` per move in `annotate_repertoire`). A move taught in learn mode is played with the hint showing, so a line whose every move sits at level 1 reads `learning` yet has never been played from memory — and the Today card and the course header both pointed at the next *unlearned* line, so the player who had just learned four White lines was still told "Learn …" ("it could show me the practise but not learn"). A correct answer in practice mode, due or early, counts one recall; a line is `practised` once every move has one. `nextCourseStep` (`lib/training/course.ts`) offers an unpractised learned line to practise before any line to learn, the Today card puts that step ahead of Black fixes and due reviews (it is the work the player just did, about two minutes), the line's chip reads "Learned · practice it" and its Practice button is primary, and a clean practice pass marks the line practised in the query cache before the server confirms. The column was backfilled from the `move_recalled` / `move_early` events, so a practice done before it existed still counts.
- **A game review pays once per game the player owns, and the server decides what a game is.** `game_reviewed` was keyed on a hash of the moves on the board, so every move played off a reviewed game — already analysed, hence "reviewed" at once — was a fresh game worth 15 XP: 39 of them in two minutes (585 XP, Grinder earned by stepping through engine lines; those rows were removed by hand). `useReviewReward` now names the game by id — the imported game's (`workspace.activeGame.id`) or the saved engine game's (`savedGameId`, which `reviewSaved` carries for a reopened game) — and a line that is nobody's game earns nothing. The server ignores the client's `request_id` for this kind: `reviewed_game_request_id` (`routers/training.py`) looks the id up in `games` or `sparring_games` for that player and derives `review:game:{id}` / `review:spar:{id}` itself, else 422. Pinned by `test_a_game_review_pays_only_for_a_game_the_player_owns_once`. Client-reported XP must always be checked against something the server holds.
- **XP, levels, streaks and badges are computed from `training_events`, append-only**, never stored as counters that can drift. XP is awarded server-side where the thing is recorded — drill answers (`POST /api/improvement/attempts` returns `xp_gained`), engine games (`/api/sparring/games`), line reviews — and only `quiz_correct`/`quiz_answer`/`game_reviewed` may be reported by the client, deduplicated by `request_id`. Streak days are the player's own (`tz`); today counts as alive until midnight. Levels are `50·L·(L−1)` XP with chess titles (Pawn → King).
- **Frontend**: the Review tab opens with `TodayCard` (goal ring, streak on the line, stakes — "N Black fixes are waiting; those lines came up in M of your games" — and the next three actions), then `OpeningCourse` (Black/White, "Fix these first" then by first move, per-line stakes in the player's own results), then drills and `AchievementsGrid`. `LineTrainer` drives the real board like the Opening Quiz does: opponent moves auto-play (`pushPosition`), a wrong move is taken back and the right one must be played by hand, and hint arrows go through the app store's `trainerArrows`, which override every other guidance arrow. `useApplyReward` turns any reward into `Celebrations` toasts (top centre, over the header's empty middle — never over a tab or the board); a reward without a profile (drills) is diffed against the cached profile so a drill can still level the player up. `TrainingChip` keeps streak/level/goal in the header.

- **The Today card offers the newest game for review** (`LatestGame`): result, opponent, opening, and "Review it", which loads the game in Explore with the Game review open — play, review, retry is the habit that turns games into lessons, and auto-sync keeps "latest" true.
- **Four loops on top of the course** (`services/training_games.py`, `routers/training.py`, `components/training/`). **Opening Rush** (`GET /api/training/rush`, `POST /rush/result`): Puzzle Rush's shape — 3 minutes, 3 lives, a best to beat — asked from the player's own repertoire, every move once, easiest plies first and shuffled within 4-ply bands; the first move of each side is skipped as a preference. The answers travel with the questions so a miss can be shown without a round trip, but the run is **scored on the server from the moves played**, stopping at the third miss; XP is 2 a correct move plus 5, capped at 60, and missed learned moves come due at once. **Repertoire check** (`POST /repertoire/check`, called by the Today card): the last 20 rapid/blitz games per colour against the served repertoire; the first departure per game is listed ("Yesterday you played 5...Nf6 and lost — your repertoire move is Qf6") and a *learned* move missed over the board after its last review drops to level 1, due now — idempotent, so re-running changes nothing. On the first corpus: 16 of 39 recent games stayed in the repertoire. **Boss fight**: a learned line's end position played out against the engine at the player's strength (`playOut` with `origin: "boss:<line id>"`, carried by the spar store and sent with the save, never stored); a win or draw pays `boss_defeated` (30 XP), a loss `boss_fought` (5), and a win or draw is celebrated as its own moment with the crown ("Boss beaten" / "Boss held to a draw", raised in `useSparringRecorder`). **Weekly rival and streak freezes** live in the profile: this week so far against last week at the same weekday, and one freeze per 250 XP (two at most) that a missed day inside a streak spends instead of the streak — `compute_streaks` walks every day from the first event, so a freeze can only have been earned before it is spent. Four achievements came with them (Quick draw, Lightning, Boss slayer, Better than last week).

- **Blunder Check trains the habit behind most of the lost points, not the openings** (`services/threats.py`, `GET /api/training/threats`, `POST /threats/answer`, `components/training/blunder-check.tsx`). After the opening, 54% of the first player's lost winning chances were a capture or check allowed or missed, and 70% of everything lost was middlegame — more than the openings could ever give back. The drills ask for the right move *before* a mistake; this shows the position *after* one of the player's own big mistakes (≥150cp, from a position not already −3, depth-paired like the drills) with the opponent to move and the player's side at the bottom, and asks for the opponent's punishment: finding it is the scan that would have stopped the move. Only replies that capture, check or mate count, and a recapture after the player's own capture is dropped (a trade gone wrong, obvious to spot) while a capture of the piece just moved (Qd4?? Nxd4) is exactly what it is for. The answer never reaches the page before the move is played; the server scores it against its pool, 5 XP spotted / 1 missed. **Answers are spaced** (`schedule`, `services/threats.py`): a miss rests a day and then leads the next set (up to half of it, oldest miss first, marked "Missed before"); a find rests a week, doubling with each find in a row to eight weeks — the scan that failed is what comes back, not a random ten. Pool on the first corpus: 400 positions (320 captures, 76 checks, 4 mates) in ~0.6s, cached stale-while-revalidate under the evidence prefix. Badge: Hawk eye (50 spotted).

- **Punish it is Blunder Check's other side** (`build_punish_pool` in `services/threats.py`, `GET /api/training/punish`, `POST /punish/answer`; the "Their mistakes" switch in `blunder-check.tsx`, remembered in `localStorage`, opened from anywhere with `openBlunderCheck('punish')`). It asks the largest habit measured (see Habits): the position right after an opponent's big mistake (≥150cp, from a position not already +3) that the player handed straight back on the next move (≥150cp), with the player to move and the opponent's move highlighted, and the answer is the engine's best move there when it is a capture, check or mate. Three plies are depth-paired (before, gift, reply, each pair within `MAX_PAIR_DEPTH_GAP`), past ply 20. Unlike `/threats`, the GET strips the answer before it reaches the page. Events `punish_found` (5 XP) / `punish_missed` (1) are spaced by the same `schedule`, and count toward the daily Blunder Check quest. The pool is cached under `improvement:threats:{user}:{floor}:punish`, so the threats invalidation drops it. First corpus: 400 positions (298 captures, 97 checks, 5 mates) in ~1.2s cold.
- **Daily quests point the day's training where the points go** (`services/quests.py`, `settle_quests` in `services/training.py`, `QuestList` in the Today card). Three a day: Blunder Check always first (spot 3), the openings second (10 moves right, counted from recalled/early moves, a learned line's moves and Rush scores alike, so the course and Rush both count), and a third stepping through drills / a game review / the Opening Quiz / an engine game. The set depends **only on the player and the day** — never on moves due or lines left, or finishing a quest could make it vanish — and every one is doable any day. Each pays 10 XP (`quest_done`) and all three open a 20 XP chest (`quests_all`, the Quest master badge at 7), with the day in the `request_id` so settling is idempotent. Every XP-earning write calls `settle_quests` before committing, with the player's `tz` (drill answers and engine games now send it too); `GET /profile` settles as a catch-all. The page diffs the quest board against the cached profile to celebrate (`newQuestRewards`), and ignores a board from another day. Quest "Go" buttons reach collapsed sections through `revealSection` (`collapsible-section.tsx`), and Explore's through `onOpenExplore`.

- **"Are you improving?" says whether the training works, including when it does not** (`services/progress.py`, `GET /api/training/progress`, `components/training/progress-card.tsx`, words in `lib/training/progress-report.ts`). The last 80 rapid/blitz games, each measured only when ≥60% of the player's moves have a depth-paired evaluation (a half-analysed game reads as a clean one): big mistakes a game (≥`BIG_ERROR`, a tenth of the game), the capture-or-check ones among them, the evaluation after move 10 by colour, the result and rating — the last 20 against the 20 before, and games since the first `training_events` row against the games before it. Measured on the first corpus: **6.5 big mistakes a game against 5.0, while the score went 40% → 75% and the rating 1598 → 1669** — so the card says "More big mistakes lately… your results are up anyway — the wins are coming despite the mistakes", never a cheer the numbers do not support. Changes under 10% read as "about the same". The trend is one series on one axis (a ten-game rolling mean, per-game hover titles, a dashed line where training started); rating is a tile beside it, never a second axis. ~0.3s, stale-while-revalidate under `improvement:progress:`.

- **"Your clock" answers "is it time trouble?" — and for the first player it was the opposite** (`services/clock.py`, `GET /api/training/clock`, `components/training/clock-card.tsx`, words in `lib/training/clock.ts`). On the main control (rapid when it has 20+ games), the last 300 games: clock left at the end of losses and wins, and every depth-paired big mistake after move 10 timed against the clock *before* the move (`clock_seconds_after + think_seconds − increment`). Measured on saint_uwe's 10-minute games: losses end with a median **5:59 of 10:00** unused; **87%** of 1,153 big mistakes came with half the clock or more, **57%** in under ten seconds, **1.4%** in time trouble; a typical one took 7s with 7:52 left. Bars show big mistakes by think time as **counts, never rates** — rates climb with think time because long thinks are the hard positions, which would read as "thinking longer causes mistakes". Verdicts `unused` / `time_trouble` / `balanced` carry opposite advice. Games that reached move 30 scored **53% ending with 10-30% of the clock, 48% with half or more, 22% under 10%** (`by_finish`), which set the challenge below.
- **Habits are measured, never assumed** (`services/habits.py`, `GET /api/training/habits`, `components/training/habits-card.tsx`, words in `lib/training/habits.ts`; Review → Progress → Habits). Measured on saint_uwe's 2,338 rapid/blitz games against a baseline of a big mistake on 11.7% of moves after move 10: **right after their own big mistake the next move was another 24.8%** of the time (25.9% vs 14.7% level, 38.5% vs 11.8% still winning — held for how the game stood); **after an opponent's big mistake they handed it straight back 38.7%** of the time (3,231 of 8,347, re-measured with one evaluation per position, so it is not one noisy search read twice); games 1-4 of a sitting scored **+3.7 points** over the ratings in the last year and games 5+ **−3.1**. Tilt after a loss and time of day did **not** show (the game after a loss scored 55%), and the card says so as good news rather than hiding it. Each habit carries the last 30 games' rate beside the whole window, so working on one shows. The newest game with ≥60% of the player's moves judged is read for the moves where a habit showed, each a button that loads the game, steps the board there and draws played/better arrows; newer unanalysed games are counted and offered for review. A sitting is games less than 30 minutes apart (`played_at` is the game's *end*); the endpoint reads the current sitting live (never cached) and the Today card shows "a good place to stop" once it reaches the measured length. `useSyncOnReturn` fetches new games when the player comes back to the tab after 3+ minutes, since the server's 3-hour auto-sync is a whole sitting late; a sync that found nothing no longer invalidates every query. Think time is the clock card's subject and is not repeated: per move it is confounded (long thinks are the hard positions — 5.4% of sub-2s moves were big mistakes, 26.9% of 40s+ ones).
- **Weekly challenges are scored from imported games, not from the app** (`services/challenges.py`, `POST /api/training/challenges/check`, `ChallengeList` in the Today card). Everything else pays for work done in the app; these pay (40 XP, `challenge_done`, badge "Took it to the board") when the week's real games show the habit: **use your clock** — 3 rapid games reaching move 30 that end with 10-30% of the clock (a flat "under half" was met most weeks without any change, since long games spend the clock anyway; ending under 10% scored worst, so the target is the middle, not the least left) — and **play your repertoire** — 3 games that follow it until it runs out (`first_departure`, shared with the repertoire check). Weeks run Monday-Sunday in the player's zone; each challenge pays once a week via `challenge:{monday}:{key}`. The board says when the newest imported game is over a day old and offers the import, because an unsynced library undercounts the week.

- **A rating goal says what the numbers show, not what motivates** (`services/rating_goal.py`, `GET /api/training/rating-goal`, `components/training/rating-goal-card.tsx`, words in `lib/training/rating.ts`). The pace is a least-squares line through the last 90 days of games (20 at least), and a date is given only for a climb of 5+ points a month — never extrapolated from a good month. The number that matters more is the score against opponents within 75 of the goal over a year, against half, which is what being rated there means. Measured on saint_uwe (rapid): 1669 now, peak 1777 on 4 July, **−40 a month over 90 days** (the July peak and August drop are in it) while the last 30 days are +55, and **33% against ~1800 players (64 games)** against 51% at their own level — so the card says "no steady climb yet… that gap is the work" and names no date. The goal defaults to the next hundred at least 100 up (1669 → 1800) and moves in 50s; it is a per-viewer choice in `localStorage`.

### Playing the engine (frontend)

- **The opponent is not Stockfish's strength limiter, and must not go back to it.** `UCI_LimitStrength`/`UCI_Elo` was tried first: at its floor (1,320) Stockfish picks from a **one-ply search plus random noise** (skill level 0 picks at depth 1+level), and the player's verdict was "it just played brainless things" — principled moves, then a piece hung to a two-move tactic. It matched the player's average loss only by playing a move a two-ply look already shows losing two pawns on **8.6%** of moves.
- **What it is instead** (`lib/sparring/sparring.ts`): a full-strength MultiPV-8 search cut off at a short horizon on the shared worker (`StockfishEngine.play` → `engine-store.playMove`, lines returned to the caller, never cached or uploaded), then `chooseSparMove` picks with p ∝ exp((score − best) / T). The opening comes from the book first: `chooseBookMove` plays master moves in proportion to their games (≥3% share, ≥20 games) for the first 30 plies, through the Theory panel's own query cache (`theoryQuery`) — engine randomness among near-equal opening moves played 1.e4 c6 2.Nf3 Qc7 3.Bc4 Qa5; with the book, 1.e4 c5 2.Nf3 d6 / 1.e4 e5 2.Nf3 Nc6 3.Bc4 Bc5. Replies wait out `sparMoveTimeMs` so they do not land instantly.
- **Calibrated exactly, not by playing games.** 69 positions from the player's rapid games (20 opening / 30 middlegame / 20 endgame), each with every legal move valued by a depth-12 judge and by searches at depths 1-8; any (horizon, T) model's expected loss per phase then follows with no sampling noise. The player (1,700 band, rapid+blitz): 38 / 94 / 70cp per move by phase, **7.2%** of moves losing 3+ pawns. Findings: every *sensible* chooser is far stronger than that — even the greedy one-ply best move loses only ~30cp — so the player's average can only be matched by visible blunders. The frontier (lowest visible-blunder rate per strength): ~30cp at 0.8% visible, ~42cp at 2.6%, ~54cp at 4.6%, ~73cp at 7.8%, ~94cp at 10.9%. At `CALIBRATION_RATING` (1,669) it plays **depth 2, T 110: ~50cp a move, 2.2% of moves losing 3+ pawns, 4.0% visibly bad** — beatable, half as brainless as the limiter. Stronger adds horizon (+1 ply per 200 points past the anchor) and halves T per 300 points; weaker only doubles T and never drops below a two-ply horizon, because a one-ply chooser is the limiter again. The opponent starts at the player's newest rapid rating and moves ±40 per rated game, stored per user under `chessgod.sparringStrength.v2.*` (v1 held `UCI_Elo` values and is ignored). Recalibrate by rerunning the table build if the chooser changes; the scripts were one-off, the method is this paragraph.
- **Only rated results move the saved strength; − / + is temporary.** A hand-picked strength is `override` in the spar store — memory only, cleared by "reset" or a reload — and games played at it are unrated. An earlier build saved − / + choices permanently; `readSparStrength` ignores any saved entry with no games behind it, which is exactly what those were. Resigning before making a move abandons the game rather than recording a loss.
- **A resolved drill can be played out against the engine** ("Play it out", `ImprovementTrainer` `onPlayOut`): from the position the drill asked about, unrated, switching to Explore. Games start through `useStartSparring` (`hooks/use-sparring.ts`) whichever button starts them. The board's guidance arrows are suppressed during a game like everything else (`useMoveMarkers`) — they were the one hint left, showing the drill's answer on the first move.
- **"Review with the engine" grades the finished game immediately** (`useAnalyzeLine`) and the review labels the sides You / Stockfish while that line is on the board (`reviewing.epoch === treeEpoch`).
- **A finished game is kept, reviewed and drilled without being asked** (`useSparringRecorder`, mounted in the dashboard; `routers/sparring.py`, migration `021_sparring_games`). On game over it saves the game (`POST /api/sparring/games`, moves replayed for legality), starts the depth-18 review, and once every move is graded — or the pool review has been seen running and stopped — posts the player's Mistake/Blunder/Missed Win moves (`collectSparringMistakes`, whose mover comes from the board's side to move, not ply parity: a played-out position can start with Black). `_sparring_candidates` merges them into the drill plan with `time_class` `engine`. **Each mistake carries its own depth and line, stored as an `analysis_results` row after the same validation as an upload**: the engine game's positions are not in `positions`, so `POST /api/analysis/evaluations` skips them and the review's evaluations never reached the server — without this the drill could never be graded. Verified end to end: a resigned 3-move game was reviewed and drilled in 7s (Qxf7+?? → Nf3, "Hanging material"). The Play panel shows the W–D–L record and the rated strength's walk.
- **A finished engine game is reviewed like a library game, and the review says when it is done.** The board's classification badges were gated on a loaded library game or a selected opening, so after a game against the engine the review graded every move and the board showed none of it (the player: "it shows the engine has 3 brilliants … but I can't see them"); `shouldShowBoardAnnotations` now takes `hasSparringReview` — the spar store's `reviewing` on the current `treeEpoch` — and the badges show the moment the game is over. The Play panel read "Reviewing the game…" until the drills were posted, which waits for the review to settle and silently stayed forever if the post failed; `reviewSettled` lives in the spar store now (`settleReview`), a failed post records `mistakesPosted: 'failed'`, and the line reads "Reviewed. Adding the drills…" / "Reviewed. The drills could not be saved this time." instead. **Every game against the engine is kept and can be reopened**: `GET /api/sparring/games` returns `start_fen` and `moves_uci`, each row of the Play panel's record is a button, and `useOpenSparringGame` replays the moves onto the board (`replayOfSparringGame`), aligns the player's side, marks the game reviewed as You / Stockfish (`reviewSaved`, never re-saved), opens the Game review page and starts the quick-depth review.
- **A sync the player did not ask for is quiet.** `useSyncOnReturn` fired three minutes after leaving the tab, and every return flashed the import banner for eight seconds and spun the Resync button even when nothing had been played (a rapid game is ten minutes a side, so most returns found nothing). It waits fifteen minutes now and passes `quiet: true` to `startImport`: `importQuiet` in the app store hides the banner and keeps the button at rest, and a quiet sync that finds nothing ends in `idle` rather than `complete`, so it leaves no trace; one that finds games turns visible and shows its result.
- **Clocks are optional and per side** (`SPAR_TIME_CONTROLS`, remembered in `chessgod.sparringTimeControl`). A move that lands at the end of the line charges its maker; stepping back and forward to the same leaf does not. The flag is checked every 100ms and follows the over-the-board rule — a draw when the side still on the clock cannot mate (`timeoutOutcome`). Clocks stop, and stay readable, when the game ends.
- **Everything that would reveal the answer is hidden while a game is on** (`useIsSparring`): auto-analysis, the eval bar, engine lines, rail analysis buttons, board annotations/book markers, move-list grades and the game review. `useSparringController` lives in the dashboard (not the panel) so reordering sections cannot remount it mid-search; `treeEpoch` on the app store ends a game when a game, drill or opening replaces the line. The opponent only moves at a leaf, which is what makes takebacks and branching work.
- **Every status bar under the board lives in that same reserved strip.** The import bar was a flex row that took its own height, so a sync starting or its result clearing moved the board every time (the player asked twice). In the workspace (`.page > .import-bar`) it overlays the 30px band the board already reserves, right-aligned beside the evaluation progress, one line, fixed height; measured with the board's rectangle before, during and after a Resync: identical. The landing page keeps it inline under the form. Anything new that reports status under the board goes in this band, never in the flow.
- **The analysis bar overlays the page bottom; the board reserves its strip.** As a flex row it took height from the workspace each time analysis started, and the board (container-unit sized) shrank 774 -> 745px and back on every search.

### Failure and empty states (frontend)

- **"Could not ask" is not "you have nothing."** `getAppAccessState` (`lib/app-access.ts`) returns a distinct `unreachable` state when the summary request fails, and `Dashboard` renders a retry screen instead of the import form — showing "import your games" to someone with a full library reads as data loss. A known game count wins over a failed refresh, so a background error never evicts someone from a working workspace. See `app-access.test.ts`.
- Verify offline behaviour by aborting `**/api/**` in Playwright rather than stopping the backend; it is deterministic and leaves the stack alone.
- **Classify the failure before choosing the screen.** `isServerUnreachable` (`lib/api-errors.ts`) is the only thing that may claim an outage: no response at all, or a 5xx. A 404 from `/api/import/{user}/summary` means "no games under that name" and must fall through to the import form — it is what a mistyped username produces, and the outage screen tells that user their stored games are safe when they have none.
- **Errors surface where the user is looking.** While an import is running or has failed, the landing screen keeps the form mounted; flipping to the "checking your library" state unmounts `UsernameForm` and discards the error it was holding.
- **Chess.com failures get translated**, not passed through: `describeImportError` (`lib/import-errors.ts`) turns a 404 on `/pub/player/...` into a spelling prompt. Unrecognised messages pass through untouched rather than becoming a vague apology.
- The header only calls someone "the active player" once `total_games > 0`; a name that turned out not to exist must not leave the header claiming to be signed in as it.
- **A failed request is never an empty result.** `PanelError` (`components/ui/panel-error.tsx`) is for "the request failed"; `EmptyState` is for "it succeeded and there was nothing in it". Reporting a failure as "no deviations found" states a fact about the user's chess that is not true. Every data hook exposes `error`, and every panel that reads one must render it — Needs Work, Analysis Coverage, Openings Health, Repertoire, Theory Deviations and Stats all do.
- `getApiErrorMessage` prefers the server's own `detail`, then falls back to a plain sentence per status class. Axios' "Request failed with status code 500" is the last resort, not the default.
- **Board pieces carry accessible names.** react-chessboard wraps each piece in its own `role="button"` draggable with no name; a labelled `role="img"` span inside supplies one by name-from-content. Without it the board is thirty-two anonymous buttons in the tab order.
- An import that finishes must say so. `ImportProgress` holds the result for `COMPLETE_VISIBLE_MS` before clearing, so an action always has a visible outcome.

### Data flow for a typical session

1. User enters a Chess.com username → `POST /api/import/{username}` streams SSE progress → games stored in Postgres.
2. Board position changes → `GET /api/tree` returns the opening tree for that FEN → displayed in `MoveTreePanel`.
3. `GET /api/theory` compares the user's moves against Lichess master stats (cached in DB, refreshed by background task).
4. Stockfish engine analyzes the current FEN in-browser; results cached in `engine-store` by FEN.
5. Theory workspace can batch-analyze unanalyzed imported positions in the browser, then sync evals to the backend so recurring mistakes can be computed from persisted eval drops plus master-deviation checks.

### Lichess sync behavior

The backend throttles and gracefully handles Lichess API errors. On `401/403/429`, sync stops for a configurable cooldown (stored in `external_sync_state` DB table).

**No transaction is open while Lichess is called** (`sync_stale_master_data`). Requests are paced seconds apart, and the loop used to hold one transaction across ~50 of them, seen idle in transaction for 2.5+ minutes, which pinned the xmin horizon so autovacuum could clean nothing anywhere. The batch is now read (positions and, in one query, their moves) and committed first, each fetch runs with the session idle, and each answer and every cooldown is committed at once. It needs `expire_on_commit=False`, as every session factory here sets; `test_sync_holds_no_transaction_while_calling_lichess` pins it. Verified live: 14 positions fetched in 3 minutes with no connection idle in transaction.

**An empty answer keeps its own, much longer TTL.** 157,466 of this library's 182,796 fetched positions (86%) came back with zero master games — positions past master play, which never gain games — and on the 30-day staleness clock the entire sync quota (~4,000 fetches/day) would be spent re-confirming them for over a month before any new position was reached. `lichess_empty_ttl_days` (365) governs a position fetched with `master_total = 0`, in the SQL staleness filter and in `cache_is_stale(last_fetched, master_total)` alike; `lichess_cache_ttl_days` (30) still governs positions with real master data. Pinned by `test_sync_does_not_re_ask_positions_lichess_already_said_were_empty`.

**The Opening Explorer requires OAuth, and without a token master theory is simply absent.** `lichess-api.yaml` (the bundled official spec) declares `security: - OAuth2: []` on the masters endpoint, so an anonymous request is a flat `401` — confirmed by hand against `explorer.lichess.org`, while `lichess.org/api` answers 200 from the same host, so it is the endpoint and not the network. `LICHESS_API_TOKEN` is therefore not a politeness knob that "reduces unauthorized responses", it is **required**; create one at `https://lichess.org/account/oauth/token/create` (no scopes needed). It also had no way in: `app/config.py` has always read `lichess_api_token`, but nothing in `docker-compose.yml` forwarded it to the backend container, so setting it could not work. It is passed now, alongside `LICHESS_EXPLORER_URL`.

Measured on the first real corpus, with the sync 401ing and re-entering a 6-hour cooldown on every cycle: **0** of 2,611,746 positions had `master_total`, and **0** of 2,635,008 `position_moves` rows had `master_game_count > 0` (7,786 had the column set, all zero). That is not a cosmetic gap — `_MISTAKES_SQL` inner-joins each decision against the master moves of its parent position, so the Theory Deviations surface can return nothing at all, and does so as an *empty state*: "no deviations found" is a claim about the player's chess, when the truth is that the data it is computed from was never fetched. It is also why the "order the opening queue by deviation from master theory" idea (see the opening-signal note above) cannot even be measured yet — the signal has no data behind it. Fix the token before attempting that experiment.

`make system-audit` reports this under `master_theory`, for the same reason it reports crawl freshness: a blocked external sync leaves no error anywhere a person looks, just a panel that is quietly empty. `deviation_surface_available` keys off `master_game_count > 0` rather than rows fetched — a row recorded with zero master games grades nothing — and `blocked_providers` names any provider sitting on a 401/403 or an unexpired cooldown. Like inert engine rows, this informs the report without failing the integrity gate: it is a missing input, not corruption.
